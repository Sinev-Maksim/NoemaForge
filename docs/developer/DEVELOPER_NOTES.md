- book_queue_entry
- chapter
- section
- normalized_text_artifact

- claim_origin

- Book identity is anchored by `book_checksum` and `book_checksum_alg`.
- Queue position is assigned before topic labeling starts.
- Chunk plans are computed before extraction starts.
- Leaf chunk bodies are processed in memory only.
- Sentence topic maps and split trees are durable.
- Metadata reuse requires checksum/profile/version match.

## Fragment 5: README

### Synthetic Books

This directory contains deterministic synthetic long-form corpora used to test the
NoemaForge hypergraph prep/extraction pipeline and grounded administrator behavior.

`book_chain_v1/` contains:
- `synthetic_book.md` — two chapters, ~10 pages each by approximate word budget
- `gold_claims.jsonl` — gold statements expected to be recoverable from extraction
- `gold_queries.jsonl` — grounded-answer query fixtures
- `manifest.json` — checksum and generation metadata

The corpus is intentionally explicit:
1. each section introduces `A` and its description
2. states that `B` follows from `A`
3. describes `B`
4. explains what the relation `A -> B` gives the system

This keeps evaluation deterministic and provenance-friendly.

## Fragment 6: BUNDLES

### Bundles (pre-start)

NoemaForge stays intentionally "bare". Anything optional (extra tools, plugins, offline repos) is treated as a **bundle** and is prepared only in **pre-start/maintenance**.

This file describes the *mechanics*.

#### What is a bundle

A bundle is a pinned pair:

- a **manifest** (YAML) in ToolVault (`toolvault/manifests/`)
- an **artifact** in ToolVault (`toolvault/artifacts/`) referenced by `artifact_sha256`

Supported manifest kinds (MVP):

- `ToolPlugin` — a plugin bundle (executed via handler=`plugin`)
- `AptRepoBundle` — a tar.gz containing an offline APT repository layout

#### Why bundles are pre-start only

Because this is the spinal-zone rule:

- no surprise installs during runtime
- no dynamic toolchain mutations by executor roles
- changes are auditable and epoch-controlled

#### BundlePolicy

See `configs/bundle-policy.yaml` (contract).

Key defaults:

- `require_lock: true` — bundle requests must include explicit `manifest_sha256` + `artifact_sha256`
- `system_package_installs.enabled: false` — to keep the base OS minimal

#### Workflow: stage artifact offline

You can stage a file into ToolVault artifacts:

```bash
brainctl toolvault import /path/to/something.tar.gz
```

This prints:

- `artifact_sha256`
- `artifact_path` (ToolVault)

Then you create a manifest under ToolVault (`toolvault/manifests/<bundle_id>.yaml`) that references that sha.

#### Workflow: request bundle preparation

In your PreStartChangeRequest, add `requested_changes.bundles_add` items as objects:

```yaml
requested_changes:
  bundles_add:
    - bundle_id: "my.plugin.bundle"
      manifest_sha256: "<sha256 of toolvault/manifests/my.plugin.bundle.yaml>"
      artifact_sha256: "<sha256 of toolvault/artifacts/...>"
      # optional, but useful for explicitness:
      manifest_path: "/var/lib/noemaforge/toolvault/manifests/my.plugin.bundle.yaml"
      artifact_path: "/var/lib/noemaforge/toolvault/artifacts/<sha>.tar.gz"
```

Then:

1) build epoch
2) run canaries
3) apply epoch

Bundle preparation happens on `apply-epoch` (pre-start), and is written into ToolVault `installed/` with inventory records.

#### Removal

Bundle “removal” does not delete evidence.

`bundles_remove` retires bundle installs in inventory (status=`retired`). Artifacts/manifests remain.

## Fragment 7: DEBUGGING

### Debugging: быстрый и эффективный стартовый протокол

NoemaForge специально устроен так, чтобы отладка не превращалась в «а давай руками полазим везде». 
Идея простая: **BootDoctor** автоматически снимает слепки и складывает их в 2 места:

- **Полный отчёт (защищённо):** `/var/lib/noemaforge/boot/reports/`
- **Support bundle (удобно достать):** `/workspace/outbox/support/`

Support bundle содержит только диагностические данные (журналы/статусы/сводки). 
Сырой контент карантина туда не попадает.

#### 1) Если «не стартует» или сервисы падают

##### (Windows preflight) Перед первым запуском / переносом

Если ты только распаковал seed-kit на Windows и хочешь убедиться, что дерево не битое:

```powershell
powershell -ExecutionPolicy Bypass -File seed\noemaforge\tools\windows\verify_seed.ps1
powershell -ExecutionPolicy Bypass -File seed\noemaforge\tools\windows\noemaforge_check.ps1
```

`verify_seed.ps1` — строгая проверка хэшей (быстро, fail-fast).

`noemaforge_check.ps1` — многошаговый чекер: отмечает где сломалось, но продолжает дальше и
складывает отчёт в `seed\noemaforge\reports\checker\...`.

##### Шаг 1 — посмотреть что упало

```bash
systemctl --failed
systemctl status noemaforge-llm-gateway noemaforge-toolproxy noemaforge-memsentinel
```

##### Шаг 2 — забрать последние логи по сервису

```bash
journalctl -u noemaforge-llm-gateway -b --no-pager -n 200
journalctl -u noemaforge-toolproxy -b --no-pager -n 200
```

##### Шаг 3 — готовый диагностический отчёт

```bash
brainctl bootdoctor quick
```

##### Шаг 4 — собрать support bundle (для себя / чтобы перенести на другую машину)

```bash
brainctl bootdoctor bundle
ls -lah /workspace/outbox/support
```

Дополнительно (оффлайн самопроверка seed/дерева, полезно при сборке/переносе):

```bash
brainctl doctor --json
brainctl doctor --full --json
```

#### 1.1) Если ты «перевоткнул диск» в другое железо

NoemaForge теперь **сам снимает hardware fingerprint** и (опционально) генерирует
**installer plan** с тем, каких драйверов/пакетов может не хватать.

Быстрые команды:

```bash
brainctl hwscan --level summary
brainctl installer plan
```

Артефакты:
- hardware scan (если `--write`): `/workspace/outbox/hwscan/`
- installer plan: `/workspace/outbox/installer-plan/`

Идея: **система не ставит пакеты сама**, она пишет детерминированный план,
а установка/изменение контрактов происходит строго в pre-start.

#### 2) Что делает BootDoctor автоматически

- Ставит `/run/noemaforge/mode = runtime` (чтобы pre-start команды в runtime не запускались «случайно»).
- Пишет boot report (json + краткий markdown).
- Если видит `failed units` из allowlist — делает support bundle.
- На **первом запуске** (первый boot на машине) собирает **максимально полный** отчёт.
- При первом обнаружении железа или смене железа:
  - пишет `hardware fingerprint`
  - может создать `installer plan` (см. `/workspace/outbox/installer-plan/`)

#### 3) Где искать отчёты

- Полные отчёты: `/var/lib/noemaforge/boot/reports/*.json`
- Отчёты по падениям unit: `/var/lib/noemaforge/boot/onfailure/<unit>/*.json`
- Outbox (удобно забрать):
  - `/workspace/outbox/bootreports/*.md`
  - `/workspace/outbox/support/*.tar.gz`

Плюс:
- installer plan: `/workspace/outbox/installer-plan/*.md`

#### 4) Важное правило

Если проблема касается установок/политик/пакетов — это **pre-start зона**.
Runtime не должен «чинить сам себя». Runtime должен уметь:
- корректно упасть,
- записать доказательства,
- предложить следующий безопасный шаг.

## Fragment 8: PLUGINS

### ToolVault plugins (bundle tools)

NoemaForge supports externally added tools/plugins, but **only** via ToolVault,
and only **pre-start**.

#### Why

"Skills/tools/plugins" are a supply-chain risk. A malicious plugin is basically
remote code execution with your agent's permissions.

So NoemaForge uses a strict model:

* tools are **deny-by-default**
* plugin execution is sandboxed (bwrap/podman preferred)
* plugins must be **bundle-attested**: artifact sha256 + manifest sha256

#### Bundle layout

ToolVault:

```
/var/lib/noemaforge/toolvault/
  manifests/
    plugin.mytool.yaml
  artifacts/
    <sha256>   # tar.gz content, extensionless
  installed/
    plugins/
      mytool/
        <sha256>/
          ...extracted files...
          .installed
```

#### Manifest format (ToolPlugin)

Example `manifests/plugin.mytool.yaml`:

```yaml
apiVersion: noemaforge.toolplugin/v1
kind: ToolPlugin

plugin_id: mytool
artifact_format: tar.gz

# Entrypoint relative to extracted bundle root.
entrypoint: run.py

# Runtime must be allowlisted (v0.9.8: python3|bash|sh).
runtime: python3
```

#### Tool registry entry

In `tool-registry.yaml`:

```yaml
- id: plugin.mytool
  enabled: true
  risk: high
  handler: plugin
  plugin:
    plugin_id: mytool
  supply_chain:
    kind: bundle
    bundle_id: plugin.mytool
    manifest_sha256: "..."
    artifact_sha256: "..."
```

ToolProxy refuses to run plugins without valid attestation.

#### Preparation

By default `SupplyChainPolicy.plugins.runtime_prepare=false`.
That means bundles must be extracted **pre-start**.

In v0.9.8 the pre-start apply step (`brainctl prestart apply`) runs a
"prepare plugins" step before switching epochs.

## Fragment 9: ROUTINES

### NoemaForge Routines (MVP 0.10.1)

This MVP adds **two deterministic (spine) routines** that work offline and produce auditable artifacts.

#### Input folders

NoemaForge expects a simple inbox structure under `/workspace`:

- `/workspace/inbox/photos/`  — photo flow input (jpg/jpeg/png/heic/webp)
- `/workspace/inbox/bank/`    — bank exports (CSV preferred; XLSX only if `openpyxl` exists)

Bootstrap creates these folders automatically.

#### Output folders

- Photo diary:
  - `/var/lib/noemaforge/routines/diary/YYYY-MM-DD/`
    - `facts.json` — episodes + metadata
    - `diary.md` — template diary
    - `manifest.json` — inputs fingerprint + pointers

- Finance budget:
  - `/var/lib/noemaforge/routines/finance/ledger.sqlite` — cumulative ledger
  - `/var/lib/noemaforge/routines/finance/raw/` — raw file snapshots (best-effort)
  - `/var/lib/noemaforge/routines/finance/YYYY-MM/`
    - `report.md` — monthly report
    - `summary.json` — monthly summary
  - `/var/lib/noemaforge/routines/finance/YYYY-MM-DD/report.md` — daily snapshot (same content)

- Clarification inquiries:
  - `/var/lib/noemaforge/inquiries/open/*.json`

#### Running routines manually

Routines are executed by the spine:

```bash
sudo noemaforge_core run-recurring daily_photo_pipeline
sudo noemaforge_core run-recurring daily_budget_reconcile
```

By default, routines target **yesterday** (in `Europe/Lisbon` timezone), because they are intended to run as daily jobs.

##### Forcing a re-run

Casebase caching skips work if inputs didn’t change.

To force execution anyway:

```bash
sudo NOEMAFORGE_FORCE=1 noemaforge_core run-recurring daily_photo_pipeline
```

#### What this MVP does NOT do (yet)

- Photo content understanding (captioning / dog detection / “beautiful sunrise”) — requires a vision model step.
- Finance “direct app export” / RSS / API ingest — only file-based exports.
- UI to answer inquiries — inquiries are stored as JSON for now.

Those are intended brain-zone expansions.

## Fragment 10: TOOL ONBOARDING

### Tool Onboarding (v0.9.7)

NoemaForge treats tools as **high-risk**. ToolProxy is the only entrypoint.

This file defines the **workflow** for adding or enabling new tools.

#### Why a workflow?

- External tools and plugins are a supply-chain risk.
- Even safe tools can become dangerous if wired to the wrong stream.
- We want auditable, reversible changes.

#### Core objects

- **Tool Registry** (`configs/tool-registry.yaml`): what tools exist, how they are implemented, whether they are enabled.
- **Tool Policy** (`configs/tool-policy.yaml`): who can call which tools, per stream.
- **Streams Catalog** (`configs/streams.yaml`): the work domains.
- **SupplyChainPolicy** (`configs/supplychain-policy.yaml`): which tools/plugins require attestation (bundle/system/internal) before an epoch switch.

#### States

- `enabled: false` → tool exists but is **not callable**.
- `enabled: true` → tool is callable **only** where policy allows.

#### Onboarding steps (recommended)

1) **Proposal**
   - Create a proposal YAML describing the tool, intended streams, risk, data access, and rollback plan.
   - Store under: `/var/lib/noemaforge/tool_proposals/`.

2) **Static gate**
   - Automatic checks:
     - the tool id is unique
     - handler type is allowed
     - requested streams exist
     - requested data paths stay within allowed boundaries
     - policy does not accidentally grant broad permissions

3) **Canary run (offline / egress emulated)**
   - Install/enable the tool only in a canary environment.
   - Outbound effects are emulated (no real network, no real external write actions).

4) **Canary tests**
   - Deterministic outputs (within tolerance)
   - ToolProxy denies out-of-policy calls
   - Resource and time budgets respected

5) **Human approval**
   - Only after tests: merge proposal into registry + policy.

6) **Publish + rollback**
   - Keep previous version entries.
   - Roll back by flipping `enabled` or version pointer.

#### MVP helper script

Seed includes a stub helper:

- `/opt/noemaforge/src/tool_onboard.py`

Commands:

- `tool_onboard.py propose --tool-id exec.run --handler sandbox_exec --risk critical`
- `tool_onboard.py validate --proposal /var/lib/noemaforge/tool_proposals/<file>.yaml`
- `tool_onboard.py promote --proposal ...` (prints patch suggestions; does not auto-apply in MVP)

> In v0.9.0 this helper is intentionally conservative and does **not** auto-edit registry/policy.
> It generates patches for manual review.

In v0.9+ the intended path is:
- runtime (head) emits a `PreStartChangeRequest`
- pre-start (`brainctl prestart ...`) builds and switches an epoch

## Fragment 11: README

### AppArmor profiles (templates)

These are **templates** for hosts that use AppArmor (Ubuntu/Debian). The seed kit does not auto-install them.

Why templates?
- NoemaForge is designed to run on a variety of Linux hosts.
- Correct AppArmor confinement depends on the exact installation paths and service definitions.

Recommended workflow
1. Install NoemaForge seed.
2. Provision services (`brainctl provision`).
3. Customize these templates for your host paths.
4. Load profiles using `apparmor_parser` and switch to enforce with `aa-enforce`.
5. Flip `lsm-policy.yaml` from `prefer` to `require` only after canaries pass.

Files
- `noemaforge-toolproxy.profile` — ToolProxy confinement template.
- `noemaforge-webgateway.profile` — WebGateway confinement template.
- `noemaforge-localgateway.profile` — LocalGateway confinement template.

### SELinux policy (skeleton)

This directory contains **skeleton** SELinux policy sources for hosts that run SELinux (Fedora/RHEL/CentOS).

The seed kit does not attempt to compile or install SELinux modules.

Suggested workflow
1. Install NoemaForge seed.
2. Confirm SELinux is enabled and in enforcing mode (`getenforce`).
3. Start services in permissive mode and collect AVC logs.
4. Create a dedicated module for NoemaForge (toolproxy/webgateway/localgateway).
5. Switch to enforcing and then flip `lsm-policy.yaml` to `require`.

Files
- `noemaforge.te` — minimal type enforcement skeleton.

## Fragment 13: README

### NoemaForge Pipeline Console

Minimal static admin GUI for switchable-LLM pipeline control.

#### Design goal

Smallest useful dashboard for prelaunch:

- launch command composer;
- current pipeline/stage/status;
- lifecycle visualization;
- in-context handoff filename pattern;
- key metrics already present in `configs/metrics-catalog.yaml`:
  - `flow.wip`;
  - `llm.error_rate`;
  - `llm.latency_ms.p95`;
  - `sec.incidents.open`.

#### Runtime invariant

The dashboard intentionally shows `switchable LLM 1/1`. It does not model parallel model teams.

#### Optional live state

Place a generated `dashboard-state.json` next to `index.html`. If absent, the console uses a safe demo fallback.

Example file: `dashboard-state.example.json`.

#### Open locally

```bash
cd noemaforge/templates/pipeline-dashboard
python3 -m http.server 8787
# open http://localhost:8787
```

#### Generate live state from NoemaForge

```bash
noemaforge pipeline dashboard-state --out /opt/noemaforge/templates/pipeline-dashboard/dashboard-state.json
```

Useful minimal flow:

```bash
noemaforge pipeline validate
noemaforge pipeline run evolution --request 'optimize pipeline console'
noemaforge pipeline list
noemaforge pipeline advance <run_id> --stage development --status in_progress --note 'handoff accepted'
noemaforge pipeline dashboard-state --out /opt/noemaforge/templates/pipeline-dashboard/dashboard-state.json
```
