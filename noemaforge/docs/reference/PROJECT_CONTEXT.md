# NoemaForge project context

NoemaForge is being prepared as a local-first `0.32.0.alpha` prelaunch package. The active package root is `noemaforge/`; runtime contracts live in `noemaforge/src`, deterministic policies live in `noemaforge/configs`, and executable coverage lives in `noemaforge/tests`.

The current release discipline treats documentation layout as a release gate, not as a cleanup preference. Markdown that remains active must live in subfolders under `noemaforge/docs`, `helpers` or `prelaunch`. The only Markdown files allowed directly in `noemaforge/docs` are `README.md`, `Manifest.md` and `TODO.md`. Changelog and release-history text is canonical in `noemaforge/docs/history/CHANGELOG.md`.

Legacy root and top-level Markdown can contain useful historical context, but it is no longer part of the active package surface. Useful TODO content and standalone wiki pages are migrated into canonical `noemaforge/docs` locations before obsolete source files are moved to project trash. Trash is a quarantine area for normal autonomous work and is excluded from active-tree hygiene scans, release manifests and package checksums.

Legacy live-debug host names, old public-docs path mentions and raw research dumps are not allowed in the active tree. Useful prose is rewritten into neutral release language, while obsolete raw sources and duplicate legacy manifests are moved to project trash for the daily cleanup cycle.

The strict docs gate is implemented by `noemaforge/configs/docs-hygiene-policy.json` and `noemaforge/src/docs_hygiene_runtime.py`. It validates required canonical files, direct docs-root limits, forbidden documentation folders, active-file readability, canonical changelog references and checked production-AI TODO items. QA and performance tests keep the scanner deterministic on local fixtures without network or hardware dependencies. Active files that appear in directory listings but cannot be stat/read-opened are treated as release-hygiene failures rather than silently skipped.

Release-gate environment readiness is now explicit before release evidence is interpreted. `release-gate-environment-readiness-core` runs from `helpers/release_gate_environment_readiness.mjs` and reports whether Python/pytest, semantic YAML parsing and a usable bash shell are available. Missing tools are blockers for the relevant gates, not successful validation results; the checker uses no network access and no hardware probes.

The `0.32.0.alpha` release gate treats archive extraction and recheck as part of the release, not as an optional packaging step. The authoritative archive is the tarball because executable-bit metadata must survive extraction on POSIX hosts; zip artifacts, if produced, are secondary convenience outputs and must be documented as requiring permission restoration if their extractor drops mode bits. Release readiness is not claimed unless version consistency, Markdown placement, forbidden-text scans, changelog uniqueness, manifest/checksum validation, executable-bit checks and the available parse/test gates pass again from a fresh extraction.

Publication is intentionally separated from packaging. The GitHub main repository workflow is to publish only the clean allowlisted release tree after archive verification, keep generated trash and local extraction folders out of the repository, and use a reviewable commit that points back to the release-gate report and archive hash. The GitHub Wiki workflow is prose-first: wiki pages are full standalone articles copied from canonical `noemaforge/docs/wiki` pages after raw research has been integrated, not uploaded as source dumps or link-only placeholders.

Windows PowerShell remains a supported preparation environment, but release validation must account for its limits. Safe scripts use literal paths, avoid string-built destructive commands, write artifacts only inside the project or output directory, and treat missing Python, bash or YAML tooling as explicit blockers. Upload helpers and future publication scripts should be dry-run first, path-confined, and should never include project trash, local extraction folders or previous archives.

The long-range technical direction remains MultiOS without weakening the local-first constraint. Linux is the reference runtime; Windows and macOS are host/control surfaces with thin launchers, runtime health reports and explicit connector policies. Trust-adaptive governance continues through Admin, Surgeon, Scary, SR/SSR and review evidence. Edge/TinyML/OTA work remains offline-contract and backlog driven until signed manifests, fallback rules, health gates and rollback evidence are validated on real targets.

The active TODO system is split for 0.32.1 so current gates are no longer buried inside historical fragments. `noemaforge/docs/TODO.md` is the short active TODO mirror, `noemaforge/docs/backlog/CURRENT_0.32.1_TODO.md` is the detailed active gate list, `noemaforge/docs/backlog/TODO_CROSSWALK.md` maps legacy requested paths and old tasks to their current destinations, and `noemaforge/docs/backlog/HISTORICAL_TODO_ARCHIVE.md` preserves old 0.26-0.31 fragments. Root-level TODO mirrors are intentionally not recreated because they violate strict Markdown placement.
