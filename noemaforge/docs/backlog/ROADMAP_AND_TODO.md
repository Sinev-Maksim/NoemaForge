#### 0.27.4
Source: `noemaforge/docs/ASAP_PLAN_0.27.4.md`

This document converts the recent research into an execution plan with two intentionally separated workstreams:

1. **Setup / preparation simplification** — remove Windows as a requirement and collapse onboarding into one clear path.
2. **Knowledge hypergraph** — make the Administrator role useful through grounded, evolving knowledge instead of ad hoc retrieval.

##### Executive decision

**Do not pivot from the NoemaForge hypergraph to an LLM Wiki architecture.**
Instead:
- keep the hypergraph as the canonical substrate;
- borrow the best LLM Wiki ideas (persistent compilation, purpose/scope artifacts, lint/maintenance loops, human-readable wiki projection);
- treat markdown/wiki/Obsidian as a projection and operator surface, not the source of truth.

That preserves the unique NoemaForge advantages:
- safe action orchestration;
- explicit tasking and workflows;
- ToolProxy single execution path;
- epoch immutability and pre-start discipline;
- typed conflicts and provenance, not only links between pages.

##### Why this is the right split

###### Setup is the commercial bottleneck
The feedback is correct: if NoemaForge targets users who want an agent to handle complex work, the install path cannot assume Windows scripts, manual multi-step discovery, or prior system administration comfort.

###### Hypergraph is the product moat
The NoemaForge differentiator is not "pretty wiki pages" but a controlled runtime where knowledge, actions, tasks, and policy-aware role switching can share one typed substrate.

A pure LLM Wiki can become a good UX layer, but it should not replace the graph.

##### Workstream A — Setup / preparation simplification

###### Goal
From a new machine or VM to first usable Administrator session with the smallest possible number of manual decisions.

###### Target user mental model
```text
1. Create a VM (or choose host mode)
2. git clone / unpack NoemaForge
3. run ./setup.sh --mode vm --model-profile balanced
4. wait for progress
5. reboot
6. use NoemaForge
```

###### Phase A1 — Collapse to one entrypoint
**Priority: immediate**

Deliverables:
- root `setup.sh`
- optional `setup.ps1` as a parity wrapper, not the primary path
- profile-driven model selection inputs
- single onboarding doc for VM mode

Definition of done:
- no newcomer needs to discover `bootstrap/noemaforge-bootstrap.sh` and `tools/prep/noemaforge-firstboot-from-share.sh` separately
- Windows helper scripts no longer define the official onboarding story

###### Phase A2 — Cross-platform prep core
**Priority: immediate**

Deliverables:
- every prep operation available via Python or POSIX shell
- Windows `.ps1` kept only as wrappers
- Linux/macOS metadata export and Vault scan parity

Definition of done:
- a Mac/Linux user can inspect, stage, and firstboot NoemaForge without Windows

###### Phase A3 — Mode support matrix
**Priority: near-term**

Deliverables:
- **VM mode**: blessed onboarding path
- **host mode**: production-style Linux path
- **docker-dev mode**: development and CI only

Definition of done:
- docs explain clearly what works in each mode and what does not

###### Phase A4 — Progress and confidence
**Priority: near-term**

Deliverables:
- firstboot progress viewer
- final summary
- errors mapped to concrete next steps

Definition of done:
- users understand where they are stuck without reading source code

##### Workstream B — Knowledge hypergraph

###### Goal
Make the Administrator useful through grounded knowledge, explicit provenance, and typed state.

###### Phase B1 — Canonical model freeze
**Priority: immediate**

Freeze the minimum useful ontology:
- Source
- Passage
- Claim
- Entity
- Concept
- Conflict
- Trail
- TaskContext
- Decision
- Artifact

In the same phase, freeze the canonical segmentation model used during ingest:
- every sentence receives topic tagging (`topic_tags`, `topic_signature`);
- consecutive sentences with the same or strongly overlapping topic signature are merged into a candidate chunk;
- chunk formation is adjacency-aware rather than fixed-size first;
- oversize chunks are split by bounded rules (paragraph -> sentence window -> clause) with lineage preserved through `chunk_parent_id` and `chunk_split_reason`.

Definition of done:
- the graph contract stops drifting;
- ingest/output layers target a stable model;
- chunk selection is specified as part of the substrate, not left implicit in downstream retrieval.

###### Phase B2 — Administrator grounding
**Priority: immediate**

Deliverables:
- Administrator query path uses hypergraph retrieval first
- retrieval operates over topic-adjacent chunks instead of naive fixed windows
- explicit fallback behavior when knowledge is absent
- no silent hallucinated "knowledge answers"
- bounded retrieval policy: if a chunk chain would exceed the active memory/token budget, select the highest-coherence subchunks first and attach neighbors incrementally

Definition of done:
- Administrator can answer "what do we know?", "what conflicts?", "what is missing?", and "what should we ingest next?"
- retrieval remains coherent even when full chapter-scale context does not fit in memory

###### Phase B3 — Purpose/scope artifacts
**Priority: near-term**

Borrow from the LLM Wiki pattern:
- keep a purpose/scope artifact per topic or project
- use it to guide ingest, synthesis, and lint

Definition of done:
- knowledge growth becomes directional, not just additive

###### Phase B4 — Projection layer
**Priority: near-term**

Deliverables:
- wiki projection for humans
- operator summary projection for Administrator
- review/conflict projection
- task-context projection

Definition of done:
- NoemaForge gets the usability of an LLM Wiki without giving up typed semantics

###### Phase B5 — Graph lint and maintenance
**Priority: near-term**

Deliverables:
- orphan detection
- unsupported claims detection
- stale knowledge detection
- weak bridges / realm gap detection
- unresolved conflict escalation

Definition of done:
- the graph can self-report where it is weak

###### Phase B5.1 — Topic-adjacency chunking and memory-safe retrieval
**Priority: immediate**

Design rule:
- chunking starts from sentence semantics, not only from token counts;
- each sentence gets a lightweight statement of "what it is about";
- consecutive sentences sharing the same topic list (or a strongly overlapping list) are grouped into one semantic chunk;
- large semantic chunks are then split only as a second step when they exceed memory/token budgets.

Required metadata:
- `sentence_id`
- `topic_tags`
- `topic_signature`
- `adjacency_group_id`
- `chunk_id`
- `chunk_parent_id`
- `chunk_split_reason`
- `boundary_confidence`
- `chunk_token_estimate`

Failure modes to handle explicitly:
- topic drift inside a long chapter;
- one sentence bridging two neighboring topics;
- a semantically coherent chunk that still does not fit into memory;
- noisy sentence tagging producing over-fragmentation.

Definition of done:
- NoemaForge can form semantically coherent chunks automatically and still degrade safely under strict memory budgets.

##### Convergence: what "ASAP success" actually looks like

The ASAP target is **not** a perfectly polished AI OS.
It is this:

- onboarding works in one obvious path on Linux/macOS/VM;
- the system reboots into a usable first epoch;
- the Administrator can interpret a request, pick a mode, answer from grounded knowledge, manage tasks, and explain capabilities;
- human-readable wiki pages are available as a projection;
- NoemaForge remains stronger than a standalone LLM Wiki because actions, policies, tasks, and knowledge live in one safety-aware runtime.

##### Non-goals for this window

- advanced visual polish before one-command install exists
- treating Obsidian/wiki markdown as canonical truth
- expanding role count before dataset coverage and staffing quality are solid
- keeping Windows workflow visible as the default onboarding path

##### Addendum — Durable prep metadata and safe reuse

The chunking layer is **not** part of the canonical hypergraph ontology.
It is a separate long-form ingest preparation layer.

For books and other long documents NoemaForge should keep a durable prep-store with at least:
- `book` and `chapter/section` registry;
- `normalized_text_artifacts`;
- `sentences` and `sentence_topic_maps`;
- `adjacency_groups` and `split_trees`;
- `passage_origins` and `claim_origins`.

Two checksum levels are required:
- `book_checksum` for the raw or canonical book payload;
- `normalized_text_checksum` for the normalized chapter/text artifact used for offsets.

Prep metadata may be reused only when:
- `book_checksum` matches;
- `normalization_version` matches;
- `normalized_text_checksum` matches where applicable;
- chunking / segmentation policy version matches.

This prevents accidental reuse of sentence maps and claim addresses after the source book or normalization pipeline has changed.

## Fragment 9: INBOX

### Inbox (capture layer)

NoemaForge intentionally separates **capture** ("I dropped something into the system") from **canonical storage** (Library/Vault) and from **streams** (domain processing).

This document explains *where to drop files* so that the pre-start workflow can pick them up.

#### 1) Canonical stores

##### Library (books, papers, docs)

- Canonical root (Windows lab):
  - `<LabRoot>\data\Library`
- Drop new files here:
  - `<LabRoot>\data\Library\inbox\...`

On pre-start (`run_lab.cmd` / `noemaforge_lab.ps1`) NoemaForge will:

1) Move files from `Library\inbox\...` into:

- `Library\sources\inbox\...`

2) Then the library scanner will update:

- `Library\library_index.sqlite`
- `Library\library_catalog.seed.json`
- Manifests under `Library\manifests\...` (if `-AutoManifest` is enabled)

##### Vault (LLM/SLM models, adapters, bundles)

- Canonical root (Windows lab):
  - `<LabRoot>\data\Vault`
- Drop new artifacts here:
  - `<LabRoot>\data\Vault\inbox\...`

On pre-start, NoemaForge will route inbox files into:

- `Vault\models\...` (GGUF / model-ish files)
- `Vault\adapters\...` (if you pre-place under `inbox\adapters\...`)
- `Vault\bundles\...` (ZIP/TAR bundles)

Then the vault scanner updates:

- `Vault\vault_index.sqlite`
- `Vault\model_registry.seed.json`
- Manifests under `Vault\manifests\...` (if `-AutoManifest` is enabled)

#### 2) Workspace capture folders (streams input)

Workspace capture is intentionally separated:

- `<LabRoot>\data\Workspace\inbox\...`

These are *stream inputs* (photos, bank exports, video, etc.).

##### Telegram channel / inbox (offline export)

Drop Telegram exports here:

- `Workspace\inbox\tg\...`

Suggested workflow (offline):

1) Export a channel/chat from Telegram Desktop as JSON.

## Fragment 11: KNOWLEDGE HYPERGRAPH

### Knowledge Hypergraph (Stage D)

NoemaForge “knowledge hypergraph” — это каноническая база знаний (структура + provenance + realm) в SQLite
плюс слой семантического индекса (VStore) как «нерв поиска».

Идея простая:
- SQLite хранит **объекты и связи** (Source/Passage/Claim/Concept/Conflict/Trail…)
- VStore хранит **вектора** (embedding) для ускорения поиска

Важный нюанс:
- Векторная близость = «похожая тема», но **не** «логическое согласие».
- Противоречия моделируются явно объектом `Conflict`.

#### Конфиг

Контракт эпохи: `knowledge-policy.yaml`.

Там задаётся:
- где лежит `kg.sqlite`
- какие слои VStore использовать (`kg_passages`, `kg_claims`, `kg_concepts`)
- минимальная таксономия `Realm`

#### Что уже есть в v0.18.0

- `knowledge.store.KnowledgeStore` — SQLite schema + CRUD для MVP сущностей
- `knowledge.ingest.ingest_text_file` — ingestion для txt/md (параграфы → passages)
- `knowledge.trails.execute_trail` — сборка “context pack” из Trail
- `knowledge.retrieval.search_keyword` — быстрый LIKE поиск
- `knowledge.gatekeeper.run_gatekeeper` — инварианты + publication gates (passages/claims/conflicts/concepts)
- `knowledge.embedding_worker` — CPU-friendly индексатор (hash embeddings) для passages/claims/concepts
- `knowledge_maintainer` — planned поток: ingest → gatekeeper → embeddings
- Gate-aware retrieval: `search_keyword(..., min_decision=...)` и `execute_trail(..., min_decision=...)`

#### Что появится дальше

- полноценная Linkbase/Annotations и “object links”
- расширение инвариантов и gates публикации (мосты realm, lineage, annotations)
- realm-aware retrieval + bridges в trails (BridgeStep enforcement)
- специализированная сеть агентов (miner/linker/conflict/tailor)

#### Queue-first long-form ingest contract

For books and other long-form sources, NoemaForge uses a separate prep-store rather than expanding the canonical ontology.

Execution order:
1. A `Source` is enqueued and receives `book_checksum`, `book_checksum_alg`, `ingest_queue_id`, and `ingest_queue_position`.
2. The system creates a normalized text artifact and records `normalized_text_checksum`, `normalization_version`, and `canonicalization_profile`.
3. Sentence/topic labeling runs over the normalized text.
4. Topic-adjacent sentences are merged into adjacency groups and then into candidate chunks.
5. If a candidate chunk exceeds budget, it is split with durable split-tree lineage.
6. Leaf chunk bodies are materialized in memory only for extraction and linking.
7. Durable prep metadata survives; temporary chunk text is discarded after processing unless debug mode explicitly keeps it.

Durable prep metadata must outlive temporary chunks:
- `books` / `book_queue`
- `chapters` / `sections`
- `normalized_text_artifacts`
- `sentences` / `sentence_topic_maps`
- `adjacency_groups` / `split_nodes`
- `passage_origins` / `claim_origins`

This keeps the hypergraph ontology clean while still providing a full provenance path from any `Claim` back to the exact book, chapter, section, sentence span, and extraction run that produced it.

## Fragment 13: MULTIOS RUNTIME HOST BACKLOG 0.32.1

### NoemaForge MultiOS Runtime Host Roadmap — 0.32.1

Tracking ID: `NFG-PROP-0.32.1-multiOS-runtime-pack`
Status: candidate alpha backlog pack; documentation only in `0.32.1`
Runtime impact: none. This does not add Windows/macOS launchers, runtime connectors, Docker dependencies, Ollama, MLX, vLLM, SSH, or remote HTTP runtime requirements to the active install.

#### Goal

Prepare NoemaForge for a future architecture where Linux remains the reference runtime while Windows and macOS can act as first-class host/control nodes.

Current principle:

```text
NoemaForge = orchestration platform
Host OS = linux | windows | macos
Runtime = local_process | WSL2 | Docker | remote Linux | Ollama | MLX | llama.cpp | vLLM | remote HTTP gateway
```

#### Design decisions

- Keep Linux as the reference production runtime for systemd, NVIDIA/CUDA, long-running services, headless deployment and predictable permissions.
- Treat Windows and macOS as first-class control/authoring/UI hosts.
- Do not force local heavy inference on weak Windows/macOS hosts.
- Prefer a runtime gateway when the host is resource constrained.
- Preserve existing Linux launcher/systemd behaviour until the abstraction layer is proven.

#### Proposed architecture layer

```text
noemaforge/runtime/
  os_probe.py
  hardware_probe.py
  registry.py
  selector.py
  base.py
  connectors/
    local_process.py
    remote_http.py
    remote_ssh.py
    ollama.py
    mlx.py
    llamacpp.py
    vllm.py
  launchers/
    darwin.py
    windows.py
    linux.py
```

#### Future CLI surface

```text
noemaforge runtime detect
noemaforge runtime list
noemaforge runtime select --profile auto
noemaforge runtime health
noemaforge launch
noemaforge launch --host-ui
noemaforge launch --runtime remote_linux
```

#### Acceptance criteria for a future implementation

1. Linux backward compatibility remains intact.
2. Windows host detection works without enabling local heavy inference by default.
3. macOS host detection works and can report Apple Silicon vs Intel.
4. Control-only mode can connect to a remote runtime gateway.
5. Remote runtime mode exposes health and readiness checks.
6. Runtime health report includes host OS, hardware summary, runtime type, selected connector, readiness, and security notes.

#### Non-goals for `0.32.1`

- No universal Windows shell replacement.
- No macOS Finder replacement.
- No automatic installation of Ollama/MLX/vLLM.
- No automatic remote SSH execution.
- No heavy local inference on unsupported hosts.

## Fragment 19: ROADMAPS

### Roadmaps (SR/SSR → Surgeon)

В NoemaForge «маршрут развития» не должен быть магией в голове агента.
Он фиксируется как **артефакт**, а изменения идут через **pre-start**.

#### 1) Два слоя roadmap

##### A) Статические roadmaps по ролям (контракт эпохи)
Файл: `role-roadmaps.yaml` (внутри contract epoch)

Это "что должно быть у роли" и "какие улучшения ожидаем".

- правится только в pre-start
- версионируется вместе с эпохой
- не раскрывается исполнителям по умолчанию

##### B) Динамические сигналы / запросы (runtime)
Многие потоки и процессы могут сигналить "нам не хватает X".
Это не меняет контракты. Это формирует очередь развития.

ToolProxy tools:
- `roadmap.record` — записать сигнал (target_role + key + описание)
- `roadmap.list` — посмотреть агрегированную очередь (для привилегированных ролей)
- `roadmap.export` — выгрузить отчёт-артефакт (для хирурга/SR/SSR)

#### 2) Приоритизация Solution Architect

Повторяемость повышает приоритет:
- `unique_sources`: сколько разных источников (stream|project) запросило одно и то же
- `total_events`: сколько раз в целом

Score (по умолчанию, настраивается в `role-roadmaps.yaml`):
`score = base + repeat_weight*total_events + unique_source_weight*unique_sources`

Пример:
- stream1 просит A (uniq=1)
- stream2 и stream3 просит B (uniq=2)
→ B выше.

#### 3) Где лежат артефакты

- SQLite очередь: `/var/lib/noemaforge/roadmaps/roadmap.sqlite`
- Экспорт отчётов: `/var/lib/noemaforge/roadmaps/exports/roadmap_report_*.json|*.md`

#### 4) Рекомендованный ритуал

1) Потоки/PM записывают `roadmap.record` при повторяющихся проблемах/недостающих инструментах.
2) SR/SSR периодически делают `roadmap.export` в системном потоке `system.guard`.
3) Surgeon выбирает задачи, оформляет изменения как `PreStartChangeRequest`,
   прогоняет canaries, переключает эпоху.

## Fragment 24: WIKI INCREMENTAL PATCHES 0.30.22

### NoemaForge 0.30.22 — Wiki incremental patches

#### Goal

Every self-improvement cycle should leave an auditable wiki update showing:

- what changed functionally;
- what changed in metrics;
- which files would be changed in the wiki repository;
- how an operator can apply the patch locally.

#### Commands

```bash
noemaforge wiki-patch create   --wiki-repo /path/to/project-wiki   --source-root /opt/noemaforge   --title "Self-improvement testbench"   --description "Added testbench and telemetry gates"   --metrics-before baseline_summary.json   --metrics-after candidate_summary.json   --include docs/wiki/metrics/testbench-and-regression-metrics.md   --include docs/wiki/pipelines/wiki-incremental-patch-pipeline.md

noemaforge wiki-patch list
noemaforge wiki-patch apply --patch-dir /var/lib/noemaforge/wiki_patches/<patch> --wiki-repo /path/to/project-wiki --dry-run
```

#### Patch bundle contents

```text
README.md
functional_delta.md
metrics_delta.json
patch.diff
wiki_patch_manifest.json
commit_message.txt
apply.sh
payload/
```

`apply.sh` copies payload files into a local wiki repo. It does not push to git.
