## Fragment 1: CANARY

### Canary (pre-start only) — v0.9.2

NoemaForge uses **Contract Epochs**. Changing an epoch (streams/tools/policy) is dangerous, so we gate it with a canary.

**Hard rule:**

- **No canaries run during runtime** (after the head/brain is started).
- Canaries run **only in pre-start / maintenance mode**.
- Exception: a *break-glass* operator action may override this (explicit flags), but the recommended practice is to **reboot into pre-start mode**.

#### Suites

- **SMOKE** — fast, critical checks only
  - Manifest integrity
  - Static consistency (policy references only known streams/tools)

- **FULL** — regression
  - SMOKE
  - Security fixtures (policy/registry-level tests)
  - Privilege-diff heuristics

Suite selection is a **Scary Core** responsibility: it computes the minimum required suite based on what changed.

#### Quotas

Canary quotas are **safety fuses**, not performance tuning.
Even in pre-start, a buggy test must not be able to OOM the host, fill the disk, or fork-bomb the system.

Configured in `canary-policy.yaml` (part of each epoch).

#### Scary Report

Every canary run produces a **Scary Report** artifact:

- Stored as `scary_report.json` inside the candidate epoch directory
- Logged to SEL/WORM (event: `canary_report_saved`)

`brainctl prestart apply-epoch` **refuses to switch epochs** if the Scary Report is missing or not PASS.

#### Operator flow

1) Build candidate epoch
2) Run canary (SMOKE/FULL) in pre-start (produces `scary_report.json`)
3) If PASS + approvals: switch `epochs/current`

## Fragment 2: GLOVES

### Gloves (v0.10.8)

**Gloves** are NoemaForge’ sterile, one-shot analysis workers.

They exist for one reason: when we inspect suspicious content, we want the inspector to have:

- **no long-term memory**
- **no access** to the main system’s working context
- **no network**

So a glove runs in a sandbox:

- incident snapshot mounted **read-only**
- output dir mounted **read-write**
- result copied back as stable evidence artifacts

#### Tools

Base tool:

- `glove.analyze` — generic analysis pass

Convenience tool IDs (same handler, different profile):

- `glove.web_sanitize` (profile=`web_sanitize`)
- `glove.rss_sanitize` (profile=`rss_sanitize`)
- `glove.net_inspect` (profile=`net_inspect`)
- `glove.package_inspect` (profile=`package_inspect`)
- `glove.git_scan` (profile=`git_scan`)

ToolPolicy should allow these only for `system.guard` roles (surgeon/sr/ssr/scary).

#### Evidence handling

The incident directory is evidence.

The glove process itself is not allowed to write into the incident root.
It writes into:

- `incident_dir/glove_out/` (one folder reused, one report per run)

Then the runner copies stable files into the incident root:

- `incident_dir/glove_report.json`
- optional side artifacts:
  - `incident_dir/glove_sanitized.txt` (rss/web sanitize)
  - `incident_dir/glove_payload_inventory.json` (git/package inspect)

#### What the glove report contains (seed MVP)

- summary of action/reason
- suspicious signal scan (prompt-injection / exfil / RCE hints)
- risk score (0..100)
- recommendations
- fingerprints (sha256) of snapshot artifacts
- payload presence + type guess
- multi-language pass placeholders (future: real SLM passes + diffs)

#### Why multi-language passes

Human brains get different “angles” depending on language.

In future releases, the glove runner can execute multiple small-model passes with prompts in different languages and compute structured deltas.

## Fragment 3: SANDBOX

### SandboxPolicy (v0.9.7)

NoemaForge uses **ToolProxy** as the single choke-point for tools.

`SandboxPolicy` is an **epoch-scoped contract** that defines how dangerous tools run in isolation.

#### Why this exists

- `exec.run` is a sharp knife. Without isolation it becomes a foot-gun and a data-exfiltration path.
- We want **offline-first** operation.
- We want isolation that scales from tiny IoT boxes (no containers) to big servers.

So we define a backend chain:

1) **bwrap (bubblewrap)** — namespace + mount isolation using host binaries (recommended)
2) **podman** — containers, when images are preloaded offline
3) **host** — RLIMIT-only fallback (degraded isolation)

> v0.9.7 security change: **host fallback is quarantined by default**.
> If no isolated backend is available, `exec.run` will NOT execute and ToolProxy will
> create a quarantine incident instead. Allowing host fallback requires an explicit
> pre-start epoch change authored by a human/surgeon.

#### Contract file

`/var/lib/noemaforge/contracts/epochs/<EPOCH>/sandbox-policy.yaml`

Key fields:

- `backends.preference`: backend order
- `backends.host_fallback.mode`: `allow | deny | quarantine`
- `quota_profiles.*`: safety fuses for CPU/mem/pids/files/timeout

#### What ToolProxy mounts for exec.run

ToolProxy does **not** mount arbitrary paths.

For `exec.run`, it derives mount roots from the stream allowlists:

- `streams.yaml: streams.<stream>.data_ro` → mounted RO
- `streams.yaml: streams.<stream>.data_rw` → mounted RW

Globs like `/var/lib/noemaforge/projects/**` are converted to mountable prefixes like `/var/lib/noemaforge/projects`.

#### What bwrap does (MVP)

- New namespaces (pid/uts/ipc + optional net)
- No network by default
- tmpfs for `/tmp` and `/var/tmp`
- Minimal `/etc` generated per run (to avoid leaking host secrets)
- RO-bind system binaries (`/usr`, `/bin`, `/lib*`, `/sbin`)

#### What podman does (MVP)

- `--network none` by default
- `--read-only` filesystem + tmpfs `/tmp`
- RO/RW mounts derived from the stream allowlists
- Requires offline images (`pull_policy: never`)

#### Limitations (honest)

- This is still not a microVM. Kernel attack surface remains.
- Podman images must exist locally.
- bwrap availability depends on distro + user namespaces.

Future hardening path:

- add a microVM backend (firecracker) to the same backend chain
- make per-tool images (ffmpeg/blender/etc.) part of the offline artifact store

## Fragment 4: SECURITY FIXTURES

### Security fixtures (Sword/Shield) — v0.9.2

Security fixtures are **test inputs**, not exploit payloads.

They implement an internal "Sword vs Shield" training loop:

- **Sword (Red Team)** produces fixtures that *try* to induce unsafe behavior (tool misuse, prompt injection patterns, supply-chain patterns).
- **Shield (Scary Core + ToolProxy policy gates)** must block, quarantine, and log.

#### Key rule

Fixtures are executed **only in pre-start FULL canary** (or explicit maintenance mode).

Runtime does **not** auto-run canaries.

#### Monotonicity (fixtures cannot be weakened)

To allow **adding new fixtures** and having them run immediately in the same epoch switch,
the seed kit evaluates fixtures from the **candidate epoch** during FULL canary.

To avoid "testing the tests" being compromised, a monotonicity gate is enforced:

- Candidate epoch must not delete existing fixture IDs.
- Candidate epoch must not modify existing fixture bodies.
- Candidate epoch may add new fixtures.

If a candidate attempts to remove/alter established fixtures, the canary fails.

#### What fixtures test in the seed kit

Fixtures validate the **policy+registry decision layer**:

- A request is ALLOW only if:
  - the tool action exists and is enabled in tool-registry, AND
  - tool-policy explicitly allows it for (stream_id × role)

Fixtures are stored in `security-fixtures.yaml` and versioned as part of the Contract Epoch.

#### Scary Report integration

When FULL canary runs, fixture results are recorded into `scary_report.json`:

- `fixtures.total`
- `fixtures.failed`
- `fixtures.mismatches[]` (structured list of fixture mismatches)

This makes fixture failures easy to audit and diff.

#### Extending fixtures

Add fixtures by creating a pre-start change request authored by `scary` or `surgeon`, then apply a new epoch.

#### Quarantine slim samples (hash-only)

When a fixture is auto-generated from a quarantine-linked incident, brainOS may also store a
**QuarantineSlimSample**:

- It is a **gzipped JSON signature** (keys/types/lengths + hashes), **not** the raw malicious content.
- The fixture may include:

  - `sample_ref.kind: quarantine_slim/v1`
  - `sample_ref.sha256: <hash>`

This creates "space for growth": later we can evolve FULL canaries to replay specific
quarantine patterns inside a sandbox, while keeping executors blind to internal security protocol details.

## Fragment 5: STORAGE POLICY

### Storage Policy (origin-disk by default)

NoemaForge uses a **StoragePolicy** (epoch contract: `storage-policy.yaml`) to enforce:

- **Default: only the origin disk is accessible** for ToolProxy filesystem & DB tools.
- Foreign volumes can be **explicitly allowlisted** (typically **read-only**) and must be mounted under `foreign_volumes.mount_root` (default: `/mnt/foreign`).
- A periodic **Storage Guard** (systemd timer) does best-effort enforcement by unmounting / remounting foreign mounts.

Why this exists
- Portable disk workflow: move your NoemaForge disk to another machine without accidentally reading/writing random host disks.
- Reduce exfiltration surfaces (prompt injection / tool misuse).
- Make the “spine” deterministic: storage boundaries are policy, not model decisions.

#### Policy file

Location (runtime):
- Current epoch: `/var/lib/noemaforge/epochs/<epoch_id>/storage-policy.yaml` (preferred)
- Fallback: `/opt/noemaforge/configs/storage-policy.yaml`

Schema (minimal):

```yaml
apiVersion: noemaforge.storage/v1
kind: StoragePolicy

origin:
  # Filled by bootstrap --auto-origin (recommended).
  device_ptuuid: "SETUP_AUTODETECT"

foreign_volumes:
  default: "deny"        # deny | ro
  mount_root: "/mnt/foreign"
  allowlist:
    # - uuid: "...."
    #   mode: "ro"        # ro | rw (rw is strongly discouraged)
    #   require_mount_root: true
```

#### Enforcing access

##### ToolProxy hard gate
ToolProxy checks every `fs.read`, `fs.write`, and `db.*` call with StoragePolicy.
If denied:
- the tool call is blocked
- an Incident `storage_policy_violation` is opened (deduped)

##### Storage Guard (best-effort)
Provisioned as:
- `noemaforge-storage-guard.service`
- `noemaforge-storage-guard.timer`

It scans mounts and attempts to unmount foreign volumes that are not allowed.

#### Operator commands

```bash
brainctl storage status
brainctl storage scan
brainctl storage guard --dry-run
brainctl storage guard
```

#### Pre-start changes
To allow a foreign volume:
1) create a PreStartChangeRequest with `storage_policy_patch`
2) run FULL canary
3) activate new epoch

This keeps storage boundaries immutable within an epoch.

## Fragment 6: SUPPLY CHAIN

### Supply-chain защита (v0.9.7)

NoemaForge предполагает, что **tools/skills/plugins** — это *поверхность исполнения кода*.
Если разрешить «динамически подгружать и запускать» что угодно (особенно из внешнего контента) — вы получаете классические supply-chain проблемы:

- malicious skill / plugin (умышленно вредоносный)
- dependency hijack (подмена/перепаковка)
- hidden post-install payload
- "indirect prompt injection" → попытка заставить агента установить/запустить инструмент

Поэтому в NoemaForge вводится отдельный контракт **SupplyChainPolicy**.

#### Главная идея

1. **Установка/подключение инструментов — только PRE-START** (эпохи/epochs).
2. Всё, что включено в runtime, должно быть:
   - либо **internal** (поставляется внутри epoch/seed),
   - либо **system** (ставится оффлайн из зафиксированного набора пакетов: apt snapshot / nix derivation),
   - либо **bundle** (оффлайн-артефакт, закреплённый sha256 + manifest).

3. Если инструмент требует attestation, но она отсутствует/битая — epoch switch должен **провалить canary**.

#### Контракт

Файл:

`/var/lib/noemaforge/contracts/epochs/<EPOCH>/supplychain-policy.yaml`

Он определяет:

- где лежит локальный **Tool Vault** (артефакты + манифесты)
- какие категории инструментов требуют attestation
- насколько строго валить canary (FULL suite = fail)

#### Tool Vault (рекомендованная структура)

```
/var/lib/noemaforge/toolvault/
  manifests/
    <bundle_id>.yaml
  artifacts/
    <artifact_sha256>
```

#### Как это связывается с tool-registry

Для tool-registry entry можно добавить блок:

```yaml
supply_chain:
  kind: bundle   # internal | system | bundle
  bundle_id: ffmpeg
  manifest_sha256: "..."
  artifact_sha256: "..."
  # optional:
  manifest_path: /var/lib/noemaforge/toolvault/manifests/ffmpeg.yaml
  artifact_path: /var/lib/noemaforge/toolvault/artifacts/<sha>
```

В v0.9.7 это в первую очередь **проверка перед epoch switch**.
Runtime исполнители не должны иметь возможность "самостоятельно" подключать новый инструмент.

#### Примечание

Это не замена sandbox/микроVM, а отдельный слой:

- sandbox отвечает за *изоляцию исполнения*
- supply-chain policy отвечает за *доверие к самому инструменту* (что мы вообще запускаем)

## Fragment 7: quantization policy

### NoemaForge quantization policy

Default recommendation: **Q4_K_M**.

#### Machine tiers

- `<8GB RAM`: 0.3B-1.5B Q4_K_M/Q5_K_M; Q8_0 only for tiny models.
- `8-16GB RAM`: 1.5B-3B Q4_K_M; 7B Q4_K_S only for tests.
- `16-32GB RAM`: 3B Q4_K_M safe main; 7B/8B Q4_K_M next-round tests; 14B headless/test only.
- `32-64GB RAM`: 7B/8B Q4_K_M/Q5_K_M main; 14B Q4_K_M tests.
- `64GB+ RAM`: 14B Q4_K_M/Q5_K_M main candidates; 32B Q4_K_M test/headless.

#### NoemaForge policy

Given ~16GB RAM and RTX 3080 Ti 12GB VRAM:

```text
safe main: Qwen2.5-Coder-3B-Instruct Q4_K_M
next tests: Qwen Coder 7B Q4_K_M, Granite 8B Q4_K_M, Phi-4-mini Q4_K_M
avoid main: 14B+ while GUI is active
avoid runtime: 32B+ on this machine
```

Use:

```bash
noemaforge recommend-model
noemaforge recommend-model --json
```
