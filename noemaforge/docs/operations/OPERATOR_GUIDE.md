## Fragment 1: AUTOSTART BOOT MODES 0.30.20

### NoemaForge 0.30.20 — conditional safe autostart boot modes

NoemaForge no longer treats autostart as a raw `enable noemaforge-llama@main.service` action. The only supported autostart path is **gated safe-start**:

- `manual`: no runtime autostart.
- `gui`: start NoemaForge runtime **after** `display-manager` / GUI is active.
- `wogui`: start NoemaForge runtime under `multi-user.target`, **instead of** GUI.

This preserves the current NoemaForge safety lesson: a heavy Qwen/NoemaForge LLM must not compete with GDM during early boot. The launcher waits for the selected mode and then runs the same memory/runtime checks as `sudo noemaforge safe-start --wait`.

#### Commands

```bash
sudo noemaforge boot-mode show --json
sudo noemaforge boot-mode set manual --apply-systemd
sudo noemaforge boot-mode set gui --apply-systemd
sudo noemaforge boot-mode set wogui --apply-systemd
```

#### GUI mode

```bash
sudo noemaforge boot-mode set gui --apply-systemd
```

Systemd default target becomes `graphical.target`. NoemaForge runtime starts only after the display manager has started:

```text
graphical.target / display-manager
→ noemaforge-autostart-gui.service
→ noemaforge-autostart-safe.sh --mode gui
→ noemaforge safe-start --wait --skip-if-running
```

#### woGUI mode

```bash
sudo noemaforge boot-mode set wogui --apply-systemd
```

Systemd default target becomes `multi-user.target`. NoemaForge runtime starts as the headless workload instead of a graphical desktop:

```text
multi-user.target
→ noemaforge-autostart-wogui.service
→ noemaforge-autostart-safe.sh --mode wogui
→ noemaforge safe-start --wait --skip-if-running
```

If a display manager is unexpectedly active in `wogui` mode, autostart blocks by default.

#### Safe-start invariants

The gate keeps:

- `max_active_llms=1`;
- backend-manager/modelscan timers disabled unless explicitly requested;
- minimum available RAM check;
- non-head GGUF shard rejection;
- stale socket cleanup;
- backend health wait.

#### Dry-run

```bash
sudo noemaforge autostart-safe --mode gui --dry-run --json
sudo noemaforge autostart-safe --mode wogui --dry-run --json
```

## Fragment 3: BOOT POLICY 0.31.03

### NoemaForge 0.31.03 — GUI/woGUI autostart policy

This release separates **boot mode** from **LLM profile**.

#### Policy

```text
gui mode:
  NoemaForge UI/dashboard/runtime start allowed
  ToolProxy allowed
  CPU bootstrap LLM optional
  heavy LLM disabled -> manual only

wogui mode:
  CPU bootstrap LLM allowed
  heavy LLM only explicit/manual
```

#### Defaults

```text
boot-mode=manual by default
GUI profile default=runtime_only
woGUI profile default=bootstrap_cpu_llm
heavy_llm_autostart=manual_only
max_active_llms=1
```

#### Commands

Show status without sudo:

```bash
noemaforge boot-mode status
noemaforge boot-mode show --json
```

Enable GUI-mode runtime-only autostart:

```bash
sudo noemaforge boot-mode set gui --apply-systemd
sudo noemaforge boot-mode set-profile gui runtime_only
```

Enable optional CPU bootstrap LLM in GUI mode:

```bash
sudo noemaforge boot-mode set-profile gui bootstrap_cpu_llm
```

Enable woGUI/headless mode:

```bash
sudo noemaforge boot-mode set wogui --apply-systemd
# default profile is bootstrap_cpu_llm
```

Manual heavy LLM start:

```bash
sudo systemctl start noemaforge-llama@main.service
```

#### Why

NoemaForge testing showed that GUI boot, ToolProxy readiness, and LLM startup must be independent layers. GUI boot must not require a heavy backend. CPU bootstrap LLM can be useful, but in GUI mode it must be opt-in. Heavy models remain manual-only.

## Fragment 4: DRIVER VAULT

### Driver Vault (offline hardware enablement)

Driver Vault is a simple offline cache for firmware/microcode driver packages.

It exists because NoemaForge aims to be:

- offline-first
- portable across hardware (move the disk to another machine)
- minimal at runtime

So instead of shipping every possible driver into the initramfs, we ship a vault
of **.deb packages** that can be installed on-demand (in pre-start mode) after
security review.

#### Seed layout

If present on the seed media:

- `seed/noemaforge/driver-vault/debs/*.deb`
- `seed/noemaforge/driver-vault/manifest.json`

Bootstrap copies these into:

- `/var/lib/noemaforge/driver-vault/debs/`

#### Building it on Windows via WSL2

Inside WSL (Ubuntu/Debian):

```bash
sudo apt update
sudo apt install -y python3 python3-yaml

bash /mnt/c/noemaforge/seed/noemaforge/bootstrap/build-driver-vault-wsl.sh \
  /mnt/c/noemaforge/seed/noemaforge
```

By default, the script downloads packages listed in `configs/installer-policy.yaml`
`bundle_catalog` (excluding `driverpack-nvidia`, unless explicitly requested).

To include nvidia-driver too:

```bash
bash /mnt/c/noemaforge/seed/noemaforge/bootstrap/build-driver-vault-wsl.sh \
  /mnt/c/noemaforge/seed/noemaforge --include-nvidia
```

#### Runtime policy

Driver Vault is **not** auto-installed.

Expected workflow:

1. Bootstrap brings up a minimal spine.
2. Pre-start mode (policy unlocked) runs:
   - BootDoctor + hardware fingerprint
   - Scary review (glove) if new packages are introduced
3. Surgeon applies a change request that installs / activates only needed drivers.

This keeps runtime stable, reproducible, and smaller.

## Fragment 5: FIRSTBOOT QUICKFIXES 0.29.17

### Firstboot quickfixes — 0.29.17

#### Fixed smoke check under `pipefail`

`tools/prep/noemaforge-firstboot-smoke.sh` no longer uses `find | grep` for required scorecard checks. The old pattern could fail under `set -o pipefail` when `grep -q` exited after the first match.

#### Staffing quality gate semantics

`src/firstboot_orchestrator.py` now writes:

```text
/var/lib/noemaforge/bootstrap/firstboot-staffing-summary.json
```

with:

```text
staffing_state = meets_target | degraded_selected | unstaffed
```

Rules:

- selected-but-below-threshold roles become `degraded_selected`, not `N/A`;
- all-zero selected scorecards block epoch apply/reboot;
- missing mandatory core roles block epoch apply/reboot;
- mandatory core roles with viable below-target models allow continuation with an explicit warning.

Mandatory core roles default to:

- `operator.admin/administrator`
- `system.guard/surgeon`
- `dev.work/solution_architect`
- `writing.story/writer`

#### Baseline archiver

```bash
sudo noemaforge firstboot-archive
```

Creates a timestamped baseline tarball from status, events, tournament results, candidate map, staffing summary, registry and scorecards.

#### Trixie launcher preflight

```bash
noemaforge trixie-preflight --json
noemaforge trixie-preflight --json --require-running
```

The default mode is read-only and does not start or stop services.

## Fragment 6: FIRSTSTART WATCHDOG FIX 0.32.1

### NoemaForge 0.32.1 — first-start watchdog and hang fix

Tracking: `NFG-FIX-0.32.1-firststart-watchdog`

Status: implemented in `0.32.1`.

#### Source finding

NoemaForge diagnostic bundle `noemaforge_03113_firststart_hang_20260511-150449.tar.gz` showed that `sudo noemaforge first-start --normal --dry-run --show-candidates` remained in role-tournament for multiple hours while a single `llama-server-cuda` backend consumed high CPU/RAM.

Observed symptoms:

- `firstboot_orchestrator.py` ran for more than 3.5 hours.
- `llama-server-cuda` stayed active under `noemaforge-llama@...service`.
- Active models included names with `uncensored` / `aggressive` markers.
- `firstboot-status.json` mixed current `role_tournament/running` fields with stale previous `request_id`, `results`, `finished_at` and `ok=true` fields.
- `role_tournament` only wrote final results, so operators could not see the current role/model/task while a run was in progress.

#### Implemented fixes

1. **Hard per-candidate watchdog**
   - `NOEMAFORGE_TOURNAMENT_PER_MODEL_TIMEOUT` now bounds each model candidate.
   - Default: fast=120s, normal=300s, full/full_composite=600s.

2. **Hard total tournament watchdog**
   - `NOEMAFORGE_TOURNAMENT_TOTAL_TIMEOUT` bounds the whole run.
   - Default: fast=600s, normal=1800s, full/full_composite=7200s.

3. **Streaming progress artifacts**
   - `/var/lib/noemaforge/bootstrap/role-tournament-progress.json`
   - `/var/lib/noemaforge/bootstrap/role-tournament-progress.jsonl`
   - `/var/lib/noemaforge/bootstrap/model-run-records.json`

4. **Backend cleanup**
   - active backends are tracked and cleaned via atexit/SIGTERM/SIGINT handlers;
   - `stop_gguf_backend()` now uses systemd stop/kill plus process fallback by backend socket path;
   - stale sockets are removed after stop.

5. **Default safety-name filter**
   - model names/paths containing markers such as `uncensored`, `aggressive`, `jailbreak`, `abliterated`, `nsfw`, `no-guard` or `no-censor` are excluded from default first-start.
   - Override only by explicit operator choice: `--include-unverified` or `NOEMAFORGE_TOURNAMENT_INCLUDE_UNVERIFIED=1`.

6. **Fresh status writes**
   - `firstboot_status.write_status()` no longer merges with previous status documents.
   - `mark_started()` emits `run_id` and `pid`.
   - This prevents stale previous success artifacts from appearing in the current running status.

7. **Operator knobs**

```bash
sudo noemaforge first-start --normal --dry-run --show-candidates   --per-model-timeout 180   --total-timeout 1200

sudo noemaforge first-start --fast --dry-run --show-candidates   --per-model-timeout 90   --total-timeout 600
```

Optional explicit unsafe/unverified inclusion:

```bash
sudo noemaforge first-start --normal --dry-run --show-candidates --include-unverified
```

#### Expected behavior after the fix

`first-start --normal --dry-run --show-candidates` should no longer remain indefinitely on one model. If a model exceeds its budget, it is marked with one of:

- `per_model_timeout`
- `total_timeout`
- `warmup_failed`
- `default_safety_filter`

and the tournament moves on or finishes boundedly.

#### Remaining validation

This fix was syntax/smoke-tested in the package sandbox. Full measured tournament validation still belongs on NoemaForge because it requires the mounted Vault, ModelStore, systemd units and actual model runtimes.

## Fragment 7: FIRST START 0.28.2

### NoemaForge 0.28.2: GUI-safe prepare + simple first start

Recommended operator flow:

```bash
sudo noemaforge prepare-gui
noemaforge models
sudo noemaforge first-start
```

`prepare-gui` is safe to run from GNOME. It installs/checks packages, verifies
`/mnt/noemaforge-share`, detects Vault, finds `llama-server`, applies the
model-safe llama systemd override, and writes the safe GGUF model candidate
report.

`first-start` may be run from GNOME Terminal. If it detects a graphical session,
it moves the long-running work into `noemaforge-first-start.service` before the GUI
is stopped. The graphical target is softly disabled by setting the default target
to `multi-user.target` and stopping `display-manager.service`. GNOME packages are
not removed.

Restore GUI later:

```bash
sudo noemaforge headless off
```

Follow first start logs:

```bash
sudo journalctl -fu noemaforge-first-start.service
```

Model safety rule: multi-part GGUF sets are only accepted through shard 1, for
example `0001-of-0005.gguf`. Non-head shards such as `0003-of-0005.gguf` are
rejected and are visible in `/var/lib/noemaforge/bootstrap/model-candidates.safe.json`.

## Fragment 9: FULL INSTALLER LOOP FIX 0.31.06

### NoemaForge 0.31.10 — full installer loop fix

#### Problem

The 0.31.10 full package had:

```bash
install_noemaforge_0.31.10_mvp.sh -> exec ./setup.sh "$@"
setup.sh -> exec install_noemaforge_0.31.10_mvp.sh ...
```

During host install this created a repeated VM setup plan loop and left the installed CLI at an older version.

#### Fix

0.31.10 restores a real installer script and keeps `setup.sh` as a front door only.

- `setup.sh --mode vm` is non-destructive by default.
- `setup.sh --mode host` delegates to `install_noemaforge_0.31.10_mvp.sh`.
- GUI autostart remains timer-driven.
- Heavy LLM autostart remains manual-only.


#### Recursion guard

`setup.sh` now exports `NOEMAFORGE_SETUP_DEPTH` and exits with code `70` if re-entered. The selftest also fails if `install_noemaforge_0.31.10_mvp.sh` contains an `exec ... setup.sh` or `bash ... setup.sh` pattern.

#### 0.31.04
Source: `docs/LIVE_REBOOT_STABILIZATION_0.31.04.md`

This document records the issues found during NoemaForge live GUI-mode first-start testing and the fixes promoted into 0.31.10.

##### Observed failures

1. `noemaforge-bootdoctor.service` failed with `NameError: td is not defined`.
2. Secure Boot rejected the NVIDIA module after kernel changed from `6.12.85` to `6.12.86`.
3. `gui-rescue --help` could start a transient rescue job instead of printing help.
4. `noemaforge-autostart-gui.service` failed because nested `safe-start` failed.
5. `noemaforge-toolproxy.service` failed because `noemaforge-sel-fix` had a broken `noemaforge_group` call.
6. ToolProxy then failed to write `/var/lib/noemaforge/sel/segments/YYYY-MM-DD.jsonl` because current-day SEL files were root-owned and group-non-writable.
7. `noemaforge version` printed stale `0.31.01` due to reading the wrong VERSION path.
8. GUI `runtime_only` policy needed to ensure stale LLM processes are not kept alive by accident.

##### 0.31.10 behavior

- `noemaforge version` reads `/opt/noemaforge/VERSION` first.
- `noemaforge gui-diagnose` reports Secure Boot, kernel, NVIDIA signer/vermagic, MOK state, GDM state, and ToolProxy state.
- `noemaforge-sel-fix --smoke` repairs current-day SEL files and verifies append-open as user `noemaforge`.
- GUI autostart defaults to `runtime_only`.
- `runtime_only` enforces no active main backend unless `--preserve-existing-llm` is explicit.
- Heavy LLM autostart remains manual-only.

## Fragment 15: OFFLINE APT

### Offline APT for NoemaForge (builder notes)

Goal: install NoemaForge baseline packages on a machine with **no network**.

NoemaForge bootstrap (`bootstrap/noemaforge-bootstrap.sh`) prefers a local APT repo:

* `--offline-apt /path/to/aptrepo`, or
* `${SEED}/offline-apt/aptrepo` (if present on seed media), or
* `/var/lib/noemaforge/toolvault/aptrepo/_active` (if an `AptRepoBundle` was prepared), or
* `/var/lib/noemaforge/toolvault/aptrepo` (legacy / manually copied).

The repo must be a **file:** APT repository with `Packages`/`Packages.gz`.

#### Important invariant

The offline repo MUST include the same packages that the bootstrap tries to install
(`BASE_PKGS=(...)` inside `noemaforge-bootstrap.sh`).

If you build an offline repo that only contains a “small baseline”, a no-network
bootstrap will fail and (correctly) refuse to download missing dependencies.

#### Fast path on Windows (WSL2 builder)

If your dev machine is Windows, the easiest builder is **WSL2**.

From PowerShell:

```powershell
wsl --install
```

Inside WSL (Ubuntu/Debian):

```bash
sudo apt update
sudo apt install -y git python3 python3-yaml dpkg-dev
```

Then run the builder script shipped in the seed-kit:

```bash
# Example if your seed-kit lives in C:\noemaforge\seed\noemaforge
bash /mnt/c/noemaforge/seed/noemaforge/bootstrap/build-offline-apt-wsl.sh \
  /mnt/c/noemaforge/seed/noemaforge
```

This will create / refresh:

* `seed/noemaforge/offline-apt/aptrepo/`
* `seed/noemaforge/offline-apt/packages.list` (audit list)

Optional: also emit an `AptRepoBundle` (tar+manifest), useful later for ToolVault:

```bash
bash /mnt/c/noemaforge/seed/noemaforge/bootstrap/build-offline-apt-wsl.sh \
  /mnt/c/noemaforge/seed/noemaforge --emit-bundle
```

#### NoemaForge-assisted flow (recommended once you have the target disk)

On the **offline target** (or inside NoemaForge in pre-start mode), you can generate
a deterministic package plan + builder script:

```bash
brainctl offline-apt plan
```

It writes artifacts into `/workspace/outbox/offline-apt/`:

- `offline-apt-plan-*.json` (resolved package list)
- `offline-apt-plan-*.builder.sh` (builder script template)
- `offline-apt-plan-*.aptrepo-bundle.manifest.yaml` (AptRepoBundle manifest template)
- `offline-apt-plan-*.prestart-request.yaml` (bundle add skeleton with blank locks)

Then run the builder script on a networked machine to produce `aptrepo/`.

#### Manual build (Linux)

Use a Linux box with network access and the same distro family as your target
(e.g., Debian stable for Debian targets, Ubuntu 22.04 for Ubuntu 22.04, etc.).

Install builder tools:

```bash
sudo apt-get update
sudo apt-get install -y dpkg-dev
```

Create a working directory:

```bash
mkdir -p noemaforge-offline-apt/aptrepo/debs
cd noemaforge-offline-apt
```

Download packages **with dependencies**:

```bash
sudo apt-get update

# Download-only (does not install), stores .debs into the chosen cache dir.
sudo apt-get -y \
  -o Dir::Cache::archives="$PWD/aptrepo/debs" \
  --download-only \
  install --no-install-recommends \
  jq curl git nftables apparmor apparmor-utils podman uidmap slirp4netns fuse-overlayfs \
  initramfs-tools grub2-common util-linux python3 python3-yaml bubblewrap
```

Generate `Packages` and `Packages.gz`:

```bash
cd aptrepo
dpkg-scanpackages debs /dev/null > Packages
gzip -kf Packages
```

Now `aptrepo/` is ready.

#### Put it onto your seed media

Copy `aptrepo/` into the NoemaForge seed:

```bash
cp -a noemaforge-offline-apt/aptrepo /path/to/noemaforge-seed/offline-apt/
```

On bootstrap, NoemaForge will install baseline packages from this repo.

#### Notes

* Mixing distro versions (e.g., building on Ubuntu 24.04 and installing on 22.04)
  is asking for dependency grief.
* This is not yet a "fully locked" system attestation — but you can record an
  `apt-snapshot` lock post-install and pin it as a `system` attestation later.

### Admin GUI default network posture (0.33.0)

The NoemaForge Admin GUI server does not start automatically on daemon/service startup. No TCP listener is bound until the operator explicitly starts the localhost dashboard.

#### Default behavior

- **No auto-start**: The Admin GUI is not started by any systemd service or boot timer. The runtime/LLM autostart (`noemaforge-autostart-gui.timer`, `noemaforge-autostart-wogui.service`) manages only the NoemaForge runtime, not the Admin GUI server.
- **Localhost-only binding**: When started, the Admin GUI server binds exclusively to the loopback address `127.0.0.1` on port `8765`. Non-loopback bind addresses are refused by default to prevent accidental network exposure of the control plane.
- **Explicit operator start**: To launch the Admin GUI, run:

```bash
noema start
```

This one-command start performs readiness checks, ensures user-writable data directories exist, launches the Admin GUI server as a subprocess, and opens the dashboard in the browser. The server runs at `http://127.0.0.1:8765/`.

#### Alternative: background start

To launch the Admin GUI in the background without waiting:

```bash
noema start --background
```

The server process runs independently; the terminal prompt returns immediately.

#### Alternative: explicit network binding (unsupported)

To bind the Admin GUI to a non-loopback address (not recommended in production):

```bash
noema start --host <address> --allow-nonlocal-host
```

This is a development-only override. The control plane is designed for localhost operation only; binding to network addresses exposes privileged operations to the network.

#### Verify the server is not running

```bash
curl http://127.0.0.1:8765/api/health 2>&1 | head -1
```

If the server is stopped, this will fail with a connection error (e.g., `curl: (7) Failed to connect to 127.0.0.1 port 8765`).

## Fragment 18: PRESTART

### Pre-start workflow (v0.9.4)

NoemaForge has exactly one boring law:

> **Runtime is immutable.**
> Contracts (streams/tools/policy) change only in **pre-start**.

#### Why pre-start exists

The head/brain (LLMs, agents) is creative by nature.
The spine (contracts, policies, audit) must be boring by design.

So:
- runtime can **propose** changes (`PreStartChangeRequest`),
- pre-start can **apply** changes (build + switch an epoch),
- and **ToolProxy enforces** the active epoch.

#### Canary rules (important)

- **Canaries run only in pre-start / maintenance mode.**
- Runtime MUST NOT auto-run canaries.
- `brainctl prestart apply-epoch` refuses to run if runtime mode is detected.
  - break-glass path exists: `--override-runtime --i-mean-it` (not recommended)

Suite selection is a **Scary Core** responsibility. Operator can request FULL, but cannot downgrade below Scary's minimum.

##### Scary Report (mandatory)

Every **final integration canary** produces `scary_report.json` inside the candidate epoch directory.

`brainctl prestart apply-epoch` **refuses to switch epochs** if:
- the report is missing,
- the report suite mismatches the run,
- or the report decision is not PASS.

##### Build Report (mandatory)

`brainctl prestart build-epoch` emits `prestart_build_report.json`:
- clear change list (what was applied / rolled back)
- per-change canary outcomes
- trigger flags (system/policy/user)

`apply-epoch` refuses if build report is not PASS.

#### Directories

- Requests inbox (runtime writes here):
  - `/var/lib/noemaforge/requests/prestart/`

- Contracts root (epochs live here):
  - `/var/lib/noemaforge/contracts/epochs/<epoch_id>/`
  - `/var/lib/noemaforge/contracts/epochs/current -> <epoch_dir>`
  - `/var/lib/noemaforge/contracts/epochs/current_epoch.txt`

#### Minimal operator flow

1) Inspect current state

```bash
brainctl epoch status
```

2) Review proposed changes

```bash
brainctl prestart queue
```

3) Approve (human step)

```bash
brainctl prestart approve <request_id>
```

4) Unlock pre-start (human step)

```bash
brainctl prestart unlock --i-mean-it
```

5) Build a candidate epoch

```bash
brainctl prestart build-epoch --description "enable tools for finance"
```

Optional: build a **manual snapshot epoch** (no contract changes) with a required comment:

```bash
brainctl prestart build-epoch --user-comment "baseline before experiments"
```

6) Switch to the candidate epoch (verifies build artifacts + switches current epoch)

```bash
brainctl prestart apply-epoch <epoch_id>
```

7) Lock again

```bash
brainctl prestart lock
```

#### What can be changed by requests (seed kit)

`PreStartChangeRequest.requested_changes` supports deep-merge patches into:

- `streams.yaml` (`streams_patch`)
- `patterns.yaml` (`patterns_patch`)
- `tool-registry.yaml` (`tool_registry_patch`)
- `tool-policy.yaml` (`tool_policy_patch`)
- `sandbox-policy.yaml` (`sandbox_policy_patch`)
- `supplychain-policy.yaml` (`supplychain_policy_patch`)
- `bundle-policy.yaml` (`bundle_policy_patch`)
- `web-gateway-policy.yaml` (`web_gateway_policy_patch`)
- `local-gateway-policy.yaml` (`local_gateway_policy_patch`)
- `bootdoctor.yaml` (`bootdoctor_policy_patch`)
- `installer-policy.yaml` (`installer_policy_patch`)
- `quarantine-policy.yaml` (`quarantine_policy_patch`)
- `role-affirmations.yaml` (`role_affirmations_patch`)
- `verifiers.yaml` (`verifiers_patch`)
- `clarifications.yaml` (`clarifications_patch`)
- `vstore.yaml` (`vstore_patch`)
- `canary-policy.yaml` (`canary_policy_patch`)
- `security-fixtures.yaml` (`security_fixtures_patch`)

`streams_add` / `patterns_add` currently copy referenced files into `epochs/<id>/overlays/` (no auto-merge yet).

#### Epoch switch triggers (v0.9.4)

Epoch switching is allowed only when triggered by:
- (a) applied **system** contract changes,
- (b) applied **policy/affirmations** changes,
- (c) an explicit **user comment** snapshot.

No-op epoch switches without a comment are refused.

## Fragment 24: WINDOWS SECOND ATTEMPT

### Windows second attempt quick guide

#### Why 'LabRoot: cd' happens
If you paste a multi-line PowerShell command (using backticks) into CMD/Anaconda Prompt, the backticks are NOT treated as line-continuations.
Arguments can get shifted and `-LabRoot` may become `cd`, creating a stray `noemaforge\cd\data\...` tree.

#### Recommended commands (CMD / Anaconda Prompt)
From Brain root:
- `tools\windows\run_firstboot.cmd`  (recommended: runs cleanup + verify + check + lab)
- `tools\windows\run_all.cmd`        (verify + check + lab)
- `tools\windows\run_lab.cmd`        (lab only)

Notes:
- The default LabRoot is a sibling folder: `<repo>\..\noemaforge-lab`.
- You can override LabRoot by passing a path as the first argument:
  `tools\windows\run_lab.cmd "C:\\Users\\...\\noemaforge-lab"`

#### Cleanup
If you see `noemaforge\cd\data\...`, you can delete `noemaforge\cd` (it's a stray labroot).

## Fragment 26: install to disk

### Install-to-disk (plan-first)

NoemaForge seed kit is designed to be **portable** and **repeatable**.

This repo does **not** ship a destructive, auto-partitioning installer by default.
Instead it provides:
- a deterministic **installer plan** (`configs/installer-policy.yaml` + `src/installer_plan.py`)
- offline bundles (offline APT repo + driver vault)
- boot checks (BootDoctor)

#### Recommended install flow

1. Build the seed media (USB or ISO) from `seed/noemaforge/`.
2. Boot the target machine.
3. Run pre-start (`prestart`) to:
   - scan hardware
   - produce a driver plan
   - decide what must be fetched via WebGateway (strict moderation)
   - generate canary scenarios
4. Apply the plan (manual or via your own provisioning tooling).
5. Only after canaries pass, switch epochs.

#### Why no "one-click" partition script?

Partitioning and formatting is always dangerous:
- disk naming differs between machines
- multi-disk rigs are common
- a bad default is catastrophic

If you *do* want an auto-installer, create it as a separate, auditable tool and put it under:
- supply-chain checks (hash/pin)
- canaries
- paranoid review by the "Scary" role

## Fragment 27: README

### Offline APT repo (optional)

NoemaForge is designed to boot **offline**.

If your target machine has **no network**, you still need a small baseline of OS
packages (python3, bubblewrap, etc.) to run the "spine".

This directory is the *drop zone* for a local `file:` APT repository.

Expected layout:

```
offline-apt/
  aptrepo/
    Packages.gz
    Packages
    debs/
      *.deb
```

During bootstrap (`noemaforge-bootstrap.sh`), if `offline-apt/aptrepo` exists on the
seed media, NoemaForge will install baseline packages from it **without touching
network APT sources**.

How to build `aptrepo/` is documented in `docs/OFFLINE_APT.md`.
