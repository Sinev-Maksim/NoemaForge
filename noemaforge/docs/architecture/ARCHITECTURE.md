## Fragment 1: ARCHITECTURE

### NoemaForge v0.9.0 unified code point

This seed pack is a **single coherent code point** for the NoemaForge MVP:

- **BCA layer**: Backlog / Context / Artifacts
- **Serial Team mode**: **exactly 1 active role per project**, baton handoffs, wake requests
- **RoleRunner**: executes roles as **ephemeral compute units** (podman if available, host fallback)
- **ToolProxy**: the only approved role→tool entrypoint; enforces **capability tokens**
- **Contract Epochs (pre-start)**: tool registry/policy/streams/verifiers are immutable at runtime
- **Streams**: tool calls are **stream-aware** (photos.diary, finance.budget, dev.work, …) and checked against policy
- **TeamWorker**: consumes wake queue and kickstarts PM when backlog has work
- **Recurring daily tasks** with priority class `daily_sla` and verifier checks
- **Daily Auditor**: ensures all planned tasks completed
- **MemSentinel**: treats memory pressure / near-OOM as `critical` and triggers checkpoint flag

#### Runtime layout (target system)

- `/opt/noemaforge/` — code + configs + contracts
- `/var/lib/noemaforge/` — state, projects, routines, context spill, logs (SEL)
- `/var/lib/modelstore/` — models + heavy artifacts
- `/workspace/` — work IO boundary for runners
- `/run/noemaforge/` — UNIX sockets (`llm/gateway.sock`, `toolproxy.sock`, backends)

#### Project layout

`/var/lib/noemaforge/projects/<project_id>/`

- `project.yaml` — project metadata
- `backlog.yaml` — backlog items
- `artifacts/` — outputs, reports
- `team/`
  - `roster.yaml` — team template instantiated
  - `semaphore.json` — serial execution lock
  - `batons/` — BatonEnvelope JSONs
  - `wakeq/` — WakeRequest queue
    - `.inflight/` `.done/` `.deadletter/`
  - `freeze/` — per-role freeze summaries (`<role>_last.md`)

#### Services (systemd)

- `noemaforge-llm-gateway.service` (S-zone) — single local entrypoint (UNIX socket)
- `noemaforge-llama@main.service` (M-zone) — inference backend (CPU-first)
- `noemaforge-toolproxy.service` (S-zone) — capability-gated tool entrypoint
- `noemaforge-memsentinel.service` (S-zone) — memory pressure sentinel (critical events)

Timers / one-shots:

- `noemaforge-dailyplan.timer` — generates DailyPlan
- `noemaforge-auditor@*.timer` — compliance checks
- `noemaforge-recurring@<task>.timer` — runs recurring tasks
- `noemaforge-teamworker.timer` — consumes project wake queues (serial baton execution)

#### Serial Team principle

- Team roles exist as a roster, but **only one role runs at a time**.
- A wake request points to a baton.
- TeamWorker selects the next wake (by priority), acquires TeamSemaphore, then runs the role.

##### v0.9 nuance: roles are *pure compute*

In v0.9 the OS keeps file mutation deterministic:

- Roles receive **context snapshots** (baton + backlog snapshot if PM + outputs snapshot if QA)
- Roles return a **RoleResult** object (outputs as text, plus PM proposals)
- NoemaForge core writes artifacts + updates backlog + creates next batons

This is intentionally conservative. Later versions can allow read-only mounts and controlled writes via ToolProxy.

#### Streams + Tool access model

##### Streams

Every task belongs to a **stream** (domain of work), e.g.:

- `dev.work` — code projects
- `photos.diary` — photo diary pipeline
- `finance.budget` — finance/budget pipeline
- `video.drone` — drone video processing
- `blender.cinema` — Blender movie pipeline
- `modeling.3dgen` — 3D reconstruction/generation

Streams are defined in: `/opt/noemaforge/configs/streams.yaml`.

##### ToolProxy (stream-aware)

- Roles never talk to tool backends directly.
- Roles call ToolProxy with a **short-lived capability token**.
- **Every tool call MUST declare `meta.stream_id`.**
- ToolProxy checks:
  1) token validity + TTL
  2) token issued_to matches meta (run_id/role/project_id)
  3) stream exists
  4) tool is present and enabled in Tool Registry
  5) tool is allowed for (stream, role) in Tool Policy

Configs:

- Tool Registry: `/opt/noemaforge/configs/tool-registry.yaml`
- Tool Policy: `/opt/noemaforge/configs/tool-policy.yaml`

#### Clarifications: TTL applies to questions, not data

NoemaForge keeps **raw data** (photos, bank exports, videos) for statistics/anomaly search.

But user-facing **clarifications** have a time window:

- finance transaction clarifications: default 30 days
- photo episode label clarifications: default 48 hours

After the window expires:

- data stays
- questions become `expired`
- the system may mark facts as `inferred` or `unknown`, but never as `confirmed` without user input.

Config: `/opt/noemaforge/configs/clarifications.yaml`.
Contract: `inquiry.schema.json`.

#### Important constraints

- Role working memory is RAM-only and ephemeral; persistence uses **batons + artifacts + freeze summaries**.
- Any memory emergency triggers a checkpoint flag; TeamWorker pauses starting new roles.
- Default storage policy allows only the origin disk; foreign volumes are deny-by-default.

#### Contract Epochs (pre-start only)

NoemaForge treats *contracts* (streams/patterns/tool registry/tool policy/verifiers) as **immutable at runtime**.

- A **Contract Epoch** is a snapshot of those files.
- Capability tokens are **bound to epoch_id**.
- ToolProxy denies any request with a token from a different epoch.

This gives us a hard boundary: **LLM can choose streams at runtime**, but it cannot expand its own powers — only a pre-start epoch update can.

See: `docs/EPOCHS.md` and `contracts/epoch_manifest.schema.json`.

#### Vector Store (vstore)

NoemaForge includes a small **segmented vector store** used as a semantic index for long-term memory / casebase / vault.

- Append-only segments (growth without full reindex)
- Tombstones + compaction in idle windows
- Metadata filtering via SQLite

See: `docs/VSTORE.md` and `src/vstore.py`.

#### 0.31.12 Admin GUI control-plane

`0.31.12` adds an explicit Admin control-plane between the GUI and NoemaForge runtimes.

Main components:

- `src/admin_runtime.py` — routes operator text to concrete pipeline IDs and optionally creates pipeline runs.
- `src/admin_gui_server.py` — localhost-only GUI/API server for dashboard state, Admin messages, pipeline actions, Admin pipeline overlays, Dev Team direct edits/version bumps, model-evolution and shutdown.
- `src/dev_team_runtime.py` — code-development control surface. It can create a dev pipeline run or produce/apply direct patches with explicit `--apply`.
- `src/model_evolution_runtime.py` — measured evolution control cycle. It writes baseline, mutation plan, scorecard, rollback and candidate profile artifacts.

The GUI is intentionally a control-plane, not a hidden runtime launcher. The invariant remains:

- no implicit heavy LLM autostart;
- text LLM policy remains switchable with `max_active_llms=1`;
- media backends are explicit-only;
- no camera/microphone capture without an operator command;
- model evolution does not mutate weights without future backend-specific explicit adapters and rollback manifests.

Admin routing maps request families to pipeline IDs such as `dev_pipeline_member_cells`, `music_generation`, `photo_generation`, `video_generation`, `camera_mask_bridge`, `model_evolution` and `release_prep`. The browser displays command results and can shut down the GUI server through `/api/shutdown`.

#### 0.31.12 Admin GUI / Dev Team / Model Evolution control plane

0.31.12 adds a launch-facing control plane on top of the existing single-active-role/runtime invariant:

- Admin is the operator-facing router and maps natural-language requests to concrete pipelines.
- The dashboard becomes a localhost Admin GUI API; it does not start an LLM or media backend implicitly.
- Dev Team can create development pipeline runs or perform explicit `--apply` edits with diff/backup metadata.
- Model Evolution is a measured lab flow with baseline, mutation plan, scorecard and rollback gate.
- Media generation and camera/mask paths remain explicit/manual until a backend adapter is selected.

##### Frontend DOM trust boundary

Both packaged dashboards treat every Admin GUI or snapshot API field as
untrusted display data. `templates/pipeline-dashboard/app.js` and
`templates/ui-dashboard/app.js` construct dynamic views with DOM APIs and
`textContent`; they do not parse API-fed HTML. Interactive controls receive
listeners and attributes directly, and artifact navigation accepts only HTTP(S)
URLs on the localhost control-plane origin. This boundary preserves the Admin
GUI's localhost-only role without trusting persisted task, event, path, model,
or pipeline metadata as markup.


##### Direct Dev Team GUI edits

The Admin GUI exposes local-only endpoints for `write-file`, `replace` and `set-version`. These endpoints delegate to `src/dev_team_runtime.py`; destructive writes require the same explicit apply flag as CLI operations and emit diff/backup metadata.

#### 0.31.12 GGUF shard safety in multimodal discovery

The multimodal discovery layer now shares the runtime-safety stance of firstboot model discovery:

- single-file `.gguf` models are runtime candidates;
- first shards such as `model-00001-of-00005.gguf` are runtime candidates;
- non-head shards such as `model-00002-of-00005.gguf` are never runtime candidates;
- rejected non-head shards are reported under `excluded_non_head_shards` for operator visibility.

This prevents Vault scans and Admin media planning from accidentally treating a continuation shard as a launchable model.


#### 0.31.12 final Admin GUI endpoints

The Admin GUI API includes `/api/admin/ask`, `/api/admin/start`, `/api/admin/modify-pipeline`, `/api/pipeline/run`, `/api/pipeline/approve`, `/api/model-evolution/run`, `/api/dev-team/run`, `/api/dev-team/write-file`, `/api/dev-team/replace`, `/api/dev-team/set-version` and `/api/shutdown`. These endpoints are localhost-only and preserve the no-hidden-LLM/media/camera invariant. Pipeline edits write only reviewed local overlays (`configs/pipelines.local.json`) when explicitly applied.

#### 0.31.12 final RC GUI lifecycle

The final RC dashboard launcher treats the browser UI as a local control plane:

1. `noemaforge gui console start` starts the localhost Admin GUI/API only.
2. `/api/health` confirms `inside_gui_supported=true`.
3. `/api/admin/message` routes operator text such as `Првиет!`, code tasks, media tasks and model-evolution tasks.
4. Routed execution creates auditable pipeline/runtime artifacts while preserving explicit apply gates.
5. `/api/shutdown` stops the GUI server without touching LLM/media/camera services.

The launcher writes transient dashboard state to an operator-writable cache rather than mutating packaged UI files, which keeps user-started GUI sessions viable on installed systems.


#### 0.32.1 architecture notes

##### First-start selection

`first-run` remains an audit/checklist surface. Actual model selection is performed by `first-start`, `firstboot_orchestrator.py` and `role_tournament.py`.

0.32.1 introduces four selection modes:

- `fast`: first measured suitable candidate.
- `normal`: retain at least two suitable candidates where available, then choose the best.
- `full`: evaluate all runnable models.
- `full_composite N`: evaluate all runnable models, then build a composition plan from top N candidates; `N=0` removes the top-N limit before the safety enumeration cap.

All modes enforce hard constraints such as QA != Developer. Composite testing is only planned for `full_composite`.

##### Warmup-gated scoring

A model candidate must pass backend startup, socket readiness and a non-empty READY probe before eval tasks are scored. Failed, empty or loading calls receive no JSON/quality credit and are excluded from the selected pool.

##### Admin Chat architecture

The GUI is organized as:

- one user-facing chat;
- one internal model/team handoff panel;
- artifact cards for created/planned outputs;
- raw JSON hidden under a details panel;
- locale packs for user-facing strings.

Persona changes are represented by transcript lines and portrait changes rather than by raw route JSON.


#### NoemaForge 0.32.1 alpha

This alpha promotes the stateful GUI shell: persistent Admin conversation history, persona portraits with deterministic fallback avatars, SR/SSR review inbox records, telemetry panels, task governance, inactivity timer, full pipeline dock, epoch/model-selection controls, CPU/GPU device policy staging, and local-first SmartHome backlog architecture.

Important runtime policy: CPU/GPU switching is staged. The selected device policy applies on the next persona/model switch or backend restart; it does not migrate an active model.

Privileged operations such as Vault re-inventory, model-selection continuation and epoch apply are plan/job-first from the GUI. They require explicit operator approval or a terminal sudo command.

### NoemaForge 0.27.10 — Extraction Runtime

This release adds the first working runtime layer after the prep pipeline:

- stable Source publication into `kg.sqlite`
- leaf-chunk → Passage publishing
- Passage provenance into `passage_origins`
- deterministic sentence/fragment claim extraction
- Claim provenance into `claim_origins`

- optional heuristic auto-concepts with `claim -> concept` links
- CLI commands:
  - `brainctl kg extract-book`
  - `brainctl kg extract-next`
  - `brainctl kg claim-origin`

#### Important boundaries

This runtime is intentionally conservative:

- leaf chunk bodies are still handled in memory only
- claims are extracted with deterministic heuristics, not free-form generation
- claim publication requires provenance
- conflict detection and grounded Administrator routing are still follow-up phases

#### Stable IDs

The runtime uses stable IDs for:

- passages
- claims
- evidence objects
- lineage links
- claim -> concept links

This keeps reruns idempotent and prevents provenance explosion.

#### Trace level

Objects created by this runtime target `L4`:

- sentence/fragment span present
- split-leaf lineage present
- run provenance present

They are not `L5` yet because there is no adjudication/review loop in this release.

## Fragment 5: HYPERGRAPH EXECUTION ORDER 0.27.6

### Hypergraph Execution Order 0.27.6

This note clarifies the execution order for long-form source processing in NoemaForge.

#### Canonical rule

The hypergraph ontology stays unchanged:
- Source
- Passage
- Claim
- Entity
- Concept
- Conflict
- Trail
- TaskContext
- Decision
- Artifact

Chunking and sentence/topic metadata live in a separate prep-store.

#### Queue-first ingest order

1. **Enqueue the book**
   - Assign `book_id`
   - Compute `book_checksum`
   - Record `book_checksum_alg`
   - Assign `ingest_queue_id`
   - Assign `ingest_queue_position`
   - Record enqueue timestamp and source path

2. **Normalize the text**
   - Produce `normalized_text_artifact`
   - Record `normalized_text_checksum`
   - Record `normalization_version`
   - Record `canonicalization_profile`

3. **Sentence/topic labeling**
   - Segment text into sentences
   - Label each sentence with `topic_tags`, `topic_signature`, confidence
   - Persist `sentence_topic_maps`

4. **Build semantic chunk plan**
   - Merge adjacent sentences into `adjacency_groups`
   - Build candidate chunks
   - If needed, recursively split into leaf nodes and persist `split_nodes`

5. **Process chunks in memory only**
   - Materialize one leaf chunk body at a time in memory
   - Extract `Passage`, `Claim`, `Entity`, `Concept`, `Conflict`, etc.
   - Record `passage_origins` and `claim_origins`
   - Release chunk body from memory after processing

6. **Retain durable metadata, discard temporary chunk text**
   - Keep prep metadata and provenance indices
   - Discard transient chunk bodies unless explicit debug/audit retention is enabled

#### Why this order matters

- `book_checksum` and queue position make retries and reprocessing stable.
- Chunk planning happens before extraction, so extraction never defines chunk boundaries ad hoc.
- In-memory chunk processing prevents accidental growth of a second text store and limits surface area for leakage.
- Durable prep metadata is enough to reconstruct provenance and safely reuse prior work.

## Fragment 6: HYPERGRAPH SQLITE SCHEMA 0.27.7

### Hypergraph SQLite Schema Notes (0.27.7)

This release adds concrete SQLite DDL for the B-track. The schema is intentionally split into:
1. `prep_store.sqlite.sql` — durable preprocessing and provenance substrate.
2. `error_learning_loop.sqlite.sql` — reviewed error capture and improvement loop.

#### Core design rules
- Canonical ontology stays unchanged.
- Long-form preprocessing metadata lives in a separate prep-store.
- Chunk bodies are temporary and processed in memory only.
- Claim publication requires provenance.
- Metadata reuse requires matching book checksum, normalized text checksum, normalization version, and segmentation policy version.

#### Full trace target
`Source -> NormalizedTextArtifact -> Chapter/Section -> Sentence -> SentenceTopicMap -> AdjacencyGroup -> SplitNode -> Passage -> Claim -> Evidence/Argument/Issue -> Response`

#### Trace guarantees provided by the DDL
- queue position is durable at enqueue time;
- every sentence has stable offsets against a normalized text artifact;
- every split leaf is reconstructible from persisted lineage;
- every claim origin records primary address and evidence spans;
- every processing run records model/profile/prompt/policy/code version;
- every reviewed error can become a regression case and/or training delta.

## Fragment 7: LOCAL GATEWAY

### Local Gateway (localgw)

Local Gateway — это направление (direction) NoemaForge для **локального мира**: IoT, 3D‑принтеры, принтеры, камеры, домашняя автоматика.

Ключевая дисциплина безопасности:

1) **LocalGW ≠ “дать сети всем ролям”.**
   Роли‑исполнители *не получают raw network*. Они общаются с устройствами через типизированные коннекторы (API).

2) **LocalGW подчинён роли `scary`.**
   Любые действия в локальной сети проходят через протокол arming/preflight и контроль scary.

3) **Первый запуск preflight — всегда FULL.**
   Начиная со второго запуска можно выбирать smoke/full.

#### Device ID: почему не SSID

Название Wi‑Fi/SSID — это “обёртка”, оно:
- может меняться,
- может быть одинаковым в разных местах,
- не является идентификатором устройства.

Поэтому LocalGW строит `device_uid` из **стабильных аппаратных/криптографических идентификаторов**.

Приоритет полей (на будущее, по мере подключения коннекторов):
1. `tls_pubkey_sha256` / `device_cert_sha256`
2. `serial`
3. `dhcp_client_id`
4. `mac`

На MVP‑уровне обычно доступен MAC (и это не идеально: MAC можно подделать), поэтому политика допуска должна быть строгой (allowlist + мониторинг).

`device_uid` формируется как:

```
device_uid = uid_prefix + sha256(canonical_fingerprint)
```

Где `canonical_fingerprint` — нормализованный JSON/строка из доступных идентификаторов.

#### Arming protocol

LocalGW выдаёт доступ в локальный мир только после `localgw.preflight`.

Результат preflight:
- инвентаризация устройств (best‑effort)
- алерты по неизвестным устройствам
- short‑lived `lan_session_token` (capability) с TTL

Без валидного токена любые команды LocalGW запрещены.

#### Allowlist режимы (важно)

LocalGW поддерживает два режима интерпретации allowlist:

* `devices.allowlist_mode: required` — **строгий режим по умолчанию**.
  Любое устройство вне allowlist считается неизвестным (даже если allowlist пуст).
  Это означает: первый preflight на новой сети, скорее всего, уйдёт в `quarantine`
  и покажет список `unknown_device_uids`.

* `devices.allowlist_mode: permissive` — allowlist применяется только если он не пуст.
  Удобно для отладки, но хуже по безопасности.

##### Как правильно “первый раз” занести устройства

1) Включаешь LocalGW (`enabled: true`) через pre-start.
2) Делаешь `brainctl localgw preflight --suite full`.
3) Получаешь `unknown_device_uids`.
4) Генерируешь патч‑заявку allowlist:

```bash
brainctl localgw enroll --all-unknown
```

Это создаст `PreStartChangeRequest` в `/workspace/outbox/localgw/`.
Дальше — обычный путь: approve → FULL canary → apply epoch.



#### Policy patcher (pre-start): draft / lint / diff

Для LocalGW действует тот же принцип, что и для WebGW:
**политику не редактируем руками в YAML**, а генерируем `PreStartChangeRequest`.

##### Сценарий: включить LocalGW и подготовить allowlist

1) Сгенерировать заявку на включение LocalGW:

```bash
brainctl localgw policy draft --enable
```

2) Перед тем как класть заявку в очередь эпохи — прогоняем линтер и смотрим diff:

```bash
brainctl localgw policy lint --request /workspace/outbox/localgw-policy/localgw-policy-*.prestart-request.yaml --strict
brainctl localgw policy diff --request /workspace/outbox/localgw-policy/localgw-policy-*.prestart-request.yaml --color
```

3) Дальше стандартный путь pre-start: approve → build-epoch → apply-epoch (FULL на первый раз).

##### Сценарий: добавить устройства в allowlist (без `enroll`)

Можно добавить конкретные `device_uid` напрямую:

```bash
brainctl localgw policy draft --allow-device lan:<sha256hex>
```

Или попытаться автоматически подобрать всё, что сейчас видно как unknown (best-effort):

```bash
brainctl localgw policy draft --all-unknown
```

Это не заменяет `localgw enroll`, а даёт “универсальный” способ править политику через pre-start.

##### Dev/Windows/WSL: lint/diff без установленной системы

Как и в WebGW, `lint`/`diff` поддерживают `--policy-path`:

```bash
brainctl localgw policy lint --request <draft.yaml> --policy-path /mnt/c/noemaforge/seed/noemaforge/configs/local-gateway-policy.yaml
brainctl localgw policy diff --request <draft.yaml> --policy-path /mnt/c/noemaforge/seed/noemaforge/configs/local-gateway-policy.yaml --color
```


#### Connectors policy (typed device access)

LocalGW не “даёт сеть” ролям. Он даёт **типизированные коннекторы** (в seed-дереве: `octoprint`, `ipp`) — и только после arming/preflight.

Политика коннекторов хранится в `local-gateway-policy.yaml`:

- `connectors.enabled`: включить/выключить слой коннекторов.
- `connectors.allow_connectors`: явный allowlist разрешённых коннекторов.
- `connectors.deny_connectors`: явный denylist (если коннектор в обоих списках — **deny побеждает**).
- `connectors.deny_raw_sockets`: остаётся `true` (raw sockets не даём).

##### Управление коннекторами только через pre-start

Никаких ручных правок YAML в runtime: изменения делаются через `PreStartChangeRequest`.

Сценарий:

1) Сгенерировать заявку (draft):

```bash
brainctl localgw connectors draft --enable --allow octoprint --allow ipp
```

2) Проверить (lint) и посмотреть diff:

```bash
brainctl localgw connectors lint --strict
brainctl localgw connectors diff --color
```

3) Дальше стандартно: approve → build-epoch → apply-epoch (FULL на первом применении).

##### Важный инвариант безопасности

**Пустой `allow_connectors` = deny-all** (а не allow-all). Это сделано специально: безопасный дефолт важнее “удобно по ошибке”.

#### SEL/WORM

LocalGW пишет события в SEL:
- `LOCALGW_PREFLIGHT`

#### Uplink glove (v0.16.0): безопасные сетевые действия

Некоторые операции — особенно **загрузка файлов** на устройства (например GCODE в OctoPrint) —
считаются более рискованными, чем обычные `GET` запросы.

Поэтому для таких действий вводится отдельный механизм: **uplink glove**.

Ключевая идея:
- это **одноразовый** (disposable) sandbox запуск,
- внутри запуска работает **детерминированный агент** (не LLM),
- сеть разрешена, но backend должен быть безопасным (предпочтение microVM → podman slirp).

##### Включение (только pre-start)

По умолчанию uplink выключен. Нужно включить через `local-gateway-policy.yaml`:

```yaml
uplink:
  enabled: true
```

##### Ограничения

Также действует размерный лимит:

```yaml
uplink:
  max_file_mib: 200
```

И rate limit на сами uplink методы:

```yaml
rate_limits:
  overrides:
    octoprint.upload_gcode:
      window_sec: 300
      max_calls: 3
```

##### Почему это важно

1) снижает риск "случайной" утечки (uplink не держит память/контекст)
2) снижает риск supply-chain (минимум зависимостей)
3) облегчает forensic анализ: uplink события пишутся в SEL/WORM

### Prep Store and Provenance Contract for Long-Form Sources

This document separates the canonical hypergraph ontology from the ingest preparation layer.

#### 1. Canonical ontology remains unchanged

The hypergraph still contains only:
- Source
- Passage
- Claim
- Entity
- Concept
- Conflict
- Trail
- TaskContext
- Decision
- Artifact

No `Chunk` object is added to the canonical ontology.

#### 2. Durable prep-store

Long-form sources such as books require a separate prep-store.
Temporary chunk bodies may be deleted after extraction, but the following metadata must remain durable:
- books
- chapters
- sections
- normalized_text_artifacts
- sentences
- sentence_topic_maps
- adjacency_groups
- split_trees
- passage_origins
- claim_origins

#### 3. Book checksums

Each book record must store a checksum so the system can determine whether prep metadata may be reused.

Recommended fields:
- `book_id`
- `source_id`
- `book_title`
- `edition`
- `language`
- `book_checksum`
- `book_checksum_alg` (e.g. `sha256`)
- `canonicalization_profile`

Recommended semantics:
- `book_checksum` should be computed over the canonical raw book payload used by ingest.
- if the book is reconstructed from multiple files, compute the checksum over a deterministic manifest or canonical bundle representation.

#### 4. Normalized-text checksums

Claim addresses depend on normalized text and offsets, so raw-book identity alone is not enough.

Recommended fields per normalized text artifact:
- `normalized_text_artifact_id`
- `book_id`
- `chapter_id`
- `normalized_text_checksum`
- `normalized_text_checksum_alg`
- `normalization_version`
- `normalization_profile`

#### 5. Safe reuse rules

Prep metadata may be reused only when all of the following match:
- `book_checksum`
- `book_checksum_alg`
- `canonicalization_profile`
- `normalized_text_checksum` where applicable
- `normalization_version`
- chunking / segmentation policy version

Otherwise the system must invalidate and recompute the dependent prep artifacts.

#### 6. Claim provenance

Every claim must have:
- `primary_address`
- `evidence_spans[]`
- `claim_mode`

Minimum machine-resolvable address fields:
- `source_id`
- `book_id`
- `chapter_id`
- `section_id`
- `normalized_text_artifact_id`
- `sentence_start_id`
- `sentence_end_id`
- `char_start`
- `char_end`
- `passage_id`
- `split_node_id`
- `quote_fingerprint`

#### 7. Error learning hooks

The prep-store and provenance layer should feed the error-improvement loop.
Errors to capture include:
- wrong topic tags
- false/missed chunk boundaries
- wrong split decisions
- wrong or missing claim address
- unsupported claim
- bad entity or concept link

Every correction should be projectable into:
- a reviewed correction store
- a regression case
- optional future training data for the prep-labeling or extraction model

## Fragment 19: TOPIC ADJACENCY CHUNKING

### Topic-Adjacency Chunking for the NoemaForge Hypergraph

This note formalizes the chunking rule requested for the long-form ingest prep path. The chunking layer is separate from the canonical hypergraph ontology.

#### Core idea

Chunking should not start from a fixed token window.
It should start from sentence meaning.

For every sentence inside one chapter/section NoemaForge should:
1. assign one or more topic labels;
2. derive a normalized `topic_signature`;
3. scan sentences in order;
4. merge consecutive sentences that share the same or strongly overlapping topic signature into one candidate chunk.

Only after this semantic grouping step should NoemaForge ask whether the chunk fits into the active memory/token budget.

#### Default algorithm

##### Stage 1 — Sentence topic tagging
For each sentence:
- compute `sentence_id`
- compute `topic_tags`
- compute `topic_signature`
- record `section_id` / `chapter_id`

##### Stage 2 — Topic-adjacency grouping
Walk sentences in source order.

Create a new adjacency group when one of these is true:
- the topic overlap drops below threshold;
- the discourse purpose changes sharply;
- the chapter/section boundary changes;
- a hard boundary marker appears (table, list switch, heading, quoted block, code block, etc.).

Otherwise keep extending the current candidate chunk.

##### Stage 3 — Memory-safe bounded split
If the candidate chunk is too large:
- first split by paragraph boundaries;
- if still too large, split by sentence windows;
- if still too large, split by clause boundaries or micro-windows.

Every split child keeps:
- `chunk_parent_id`
- inherited `topic_signature`
- `chunk_split_reason`
- `split_depth`

#### Why this is better than naive fixed windows

Fixed windows are easy but they often:
- mix adjacent but different arguments;
- break one argument in the middle;
- lose discourse order;
- create unstable retrieval quality.

Topic-adjacency chunking preserves local semantic continuity first, then applies memory limits second.

#### Retrieval rule

Administrator and other grounded roles should retrieve:
1. the best-matching coherent chunk or subchunk;
2. then adjacent support chunks only if budget remains;
3. otherwise return a bounded answer with an explicit "knowledge is partial under current context budget" note when needed.

#### Edge cases

- A sentence can bridge two themes: allow weighted multi-topic tags.
- Long coherent passages can exceed memory: split without losing lineage.
- Noisy topic tags can over-fragment text: run chunk-lint on tiny unstable chunks.
- Chapters can contain recurring motifs: preserve chapter-local adjacency and do not merge across distant regions only because the topic labels match.

#### Required metadata fields

- `sentence_id`
- `chapter_id`
- `section_id`
- `topic_tags`
- `topic_signature`
- `adjacency_group_id`
- `chunk_id`
- `chunk_parent_id`
- `chunk_split_reason`
- `boundary_confidence`
- `chunk_token_estimate`
- `split_depth`

#### Operational consequence

This belongs in B0/B1 because it is not just a retrieval optimization.
It defines the canonical ingest contract for how NoemaForge turns source text into graph-addressable knowledge units.

#### Reuse safety and checksums

Chunk bodies may be temporary, but prep metadata must be durable and safely reusable.

For every book keep:
- `book_id`
- `book_checksum`
- `book_title`
- `edition`
- `language`
- `source_id`

For every normalized text artifact keep:
- `normalized_text_artifact_id`
- `book_id`
- `chapter_id`
- `normalized_text_checksum`
- `normalization_version`

Reuse rule:
- sentence topic maps, adjacency groups, split trees, passage origins, and claim origins may be reused only when the checksums and normalization version still match.
- if the raw book checksum changes, invalidate all prep metadata for that book.
- if only the normalization pipeline changes, invalidate normalized-text-bound metadata even when the raw book checksum is unchanged.

## Fragment 20: VSTORE

### Vector Store (vstore) (v0.9.0)

NoemaForge needs a semantic index for:

- **Solution Cache / Casebase**: “готовые решения” и похожие кейсы
- **Long-term Memory**: эпизоды, артефакты, решения, контексты
- **Knowledge Vault**: документы/код/библиотека (RAG)
- **Events**: семантический поиск по логам/наблюдениям

Для этого добавлен локальный **segmented vector store**.

#### Важный нюанс: «A» и «не A» могут быть близки

Embedding обычно кодирует *тему*, а не *логическую полярность*.
Поэтому утверждения типа:

- “Кошки полезны для здоровья”
- “Кошки не полезны для здоровья”

часто попадают рядом в embedding‑пространстве.

Это **не баг**, это сигнал: “это про одно и то же”.

Правильная схема:

1) Vector retrieval → “про то же”
2) Classifier / verifier → “поддерживает / противоречит / нейтрально”
3) В граф/гипертекст → Conflict‑объект, а не просто “похоже/не похоже”.

#### Почему segmented (append-only) дизайн

Требование: **расширение без полной переиндексации**.

Решение: LSM‑стиль:
- новые записи → пишем в активный сегмент
- сегменты запечатываются, когда достигают размера
- удаление = tombstone
- compaction (слияние) делаем в окне простоя (idle window)

#### Где лежит

По умолчанию:

`/var/lib/noemaforge/vstore/<layer>/`

Внутри:
- `meta.sqlite` — метаданные и tombstones
- `segments/seg_<id>.npz` — массивы векторов
- `segments/seg_<id>.manifest.json` — манифест сегмента (hash, count, model_id)

#### Слои (layers)

В `configs/vstore.yaml` уже есть задел:

- `working_set` (RAM‑слой; позже можно в /dev/shm)
- `casebase` (готовые решения / артефакты)
- `vault` (документы/код/библиотека)
- `events` (логи/наблюдения)

#### Инструменты ToolProxy

В v0.9.0 добавлены tool actions:

- `vstore.query`
- `vstore.upsert`
- `vstore.tombstone`

Плюс в v0.9.0 включён `llm.embed` (через локальный gateway), чтобы писать реальные embeddings,
а не фейковые векторы.

По умолчанию права ограничены policy (см. `configs/tool-policy.yaml`).

#### MVP реализация

## Fragment 21: WEB GATEWAY

### WebGateway (WebGW)

WebGateway is NoemaForge’ **strict network intake valve**.

It exists to solve one problem: **when we must touch the network, we do it through a narrow, moderated pipe**.

Core rules:

- **No raw content** is returned to executors.
- Everything is downloaded into **quarantine** as evidence.
- Promotion into system vaults is **operator-only** and gated by:
  - **glove** (amnesic inspection)
  - optional **human approval** (per channel)
  - policy lock **UNLOCKED** (for promote)

#### Channels

WebGW is channelized because “download a Debian driver package” and “ingest RSS text” are different threat models.

Built-in channels (policy-defined):

- `packages` — pre-start only, supply-chain oriented.
- `rss` — allowed in runtime (if enabled), always sanitized via glove.
- `pages` — allowlisted web pages/articles, extracted (trafilatura/readability when available) + PI scrub.
- `git` — allowed in runtime (if enabled), supply-chain oriented.
- `generic` — safe default if you add a custom channel later.

All channel behavior is defined by `web-gateway-policy.yaml` in the current Contract Epoch.

#### Lifecycle

##### 1) Fetch (always → quarantine)

Tool action (for scary role, via ToolProxy):

- `webgw.fetch { url, channel }`

Operator CLI:

```bash
brainctl webgw fetch "https://…" --channel packages
```

Result is metadata-only:

- `incident_id`
- `artifact_sha256`
- content type, bytes, redirects

##### 2) Review (glove)

Operator CLI:

```bash
brainctl webgw review <incident_id>
```

This runs the glove in a sandbox and writes:

- `glove_report.json`
- optional:
  - `glove_sanitized.txt` (rss_sanitize/web_sanitize/article_extract)
  - `glove_payload_inventory.json` (git_scan/package_inspect)

Glove sanitization performs a deterministic **PI firewall** pass:

- instruction-like lines are redacted (to avoid verbatim quoting)
- a `pi_report.json` artifact is written for audit
- if severity is `high`, promotion is denied (incident stays quarantined)

##### 3) Approve (optional)

Some channels require explicit operator approval before promotion.

```bash
brainctl webgw approve <incident_id> --comment "why we accept this intake"
```

##### 4) Promote (operator-only)

Promotion moves data from quarantine into a local vault.

```bash
brainctl webgw promote <incident_id>
```

Targets (MVP):

- `toolvault.artifact` (packages, default)
- `docsvault.rss_item` (rss, default)
- `codevault.snapshot` (git, default)

Promotion leaves quarantine evidence intact and writes `webgw_promotion.json` into the incident.



#### Policy updates (pre-start)

WebGW is **deny-by-default**. To use it you must:

1) Enable WebGW (`enabled: true`)
2) Add an allowlist domain for the intended channel (e.g. `channels.rss.network.allow_domains`)

To avoid manual YAML edits, use the policy patcher. It **emits a PreStartChangeRequest draft**.

##### Draft a policy change request

Example: enable WebGW and allow RSS from `rss.nytimes.com`:

```bash
brainctl webgw policy draft --enable --allow rss:rss.nytimes.com
```

Example: allow official Debian mirrors for `packages` channel:

```bash
brainctl webgw policy draft --enable --allow packages:deb.debian.org --allow packages:security.debian.org
```

The command prints the path to the generated request file. Then:

- copy it into the prestart request queue directory (default: `/var/lib/noemaforge/requests/prestart/`)
- approve it
- build/apply a new epoch (FULL canary the first time)

```bash
brainctl prestart approve <request_id>
brainctl prestart build-epoch --description "webgw allowlist update"
brainctl prestart apply-epoch <epoch_id> --suite full
```

You can also write the draft directly into the requests directory:

```bash
brainctl webgw policy draft --enable --allow rss:rss.nytimes.com --emit-to-requests
```

##### Dry-run helpers: lint + diff

Before you queue/approve a request, you can validate it and inspect the exact change:

Lint (static checks + safety warnings):

```bash
brainctl webgw policy lint --request /path/to/webgw-policy-*.prestart-request.yaml
```

Strict mode (treat warnings as failure):

```bash
brainctl webgw policy lint --request /path/to/webgw-policy-*.prestart-request.yaml --strict
```

Diff (unified diff):

```bash
brainctl webgw policy diff --request /path/to/webgw-policy-*.prestart-request.yaml
```

If you omit `--request`, the commands will use the **latest** draft in the default outbox directory (`/workspace/outbox/webgw-policy`).


##### Notes

- Use `channel:domain` format. `domain` may also be a full URL; the patcher will normalize to host.
- `packages` remains pre-start only by default (supply-chain posture).
- Promotion still requires quarantine + glove review (+ approval when configured).


#### Why this is strict

If an agent can browse the web freely, **indirect prompt injection** becomes the default failure mode.
WebGW is designed so that even “successful” network intake lands in quarantine first.

In other words:

> The network is lava. WebGW is the tongs.

## Fragment 22: WORM SEL

### WORM / SEL in NoemaForge (v0.9.8)

NoemaForge logs security-relevant events into a local SEL.

#### What you get

* **Daily append-only segments**: `YYYY-MM-DD.jsonl`
* **Per-segment hash chain**: `YYYY-MM-DD.chain`
* **Optional seals**: `YYYY-MM-DD.seal.json`
* **Optional anchors chain** (cross-day): `anchors.chain`

This is "blockchain-like" (hash chain), but local and single-writer.

#### Why hash chains?

Because deleting/rewriting history should leave fingerprints.

If somebody edits a past JSONL line, every following hash changes. The verify
step fails.

#### WORM hardening (best-effort)

If your filesystem supports it (typically ext4/xfs), NoemaForge *tries* to set:

* `chattr +a` on segment + chain files (append-only)
* optionally `chattr +i` on sealed files (`NOEMAFORGE_SEL_SEAL_IMMUTABLE=1`)

Root can still remove attributes — but that becomes part of incident response.

#### Operations

Verify today's segment:

```bash
sudo /opt/noemaforge/src/brainctl.py sel verify
```

Verify a specific day:

```bash
sudo /opt/noemaforge/src/brainctl.py sel verify --day 2026-02-28
```

Seal a day and advance anchors:

```bash
sudo /opt/noemaforge/src/brainctl.py sel seal --day 2026-02-28
```

Verify anchors chain:

```bash
sudo /opt/noemaforge/src/brainctl.py sel verify-anchors
```

## Fragment 23: process centric pipeline runtime 0.29.15

### Process-Centric Pipeline Runtime — 0.29.15

This release adds a NoemaForge-native pipeline scaffold inspired by reusable architectural patterns from legacy tools: coordinator, roles, tasks, hooks, artifacts and GUI control. It deliberately does not reuse legacy code.

#### Design constraints

- Switchable LLMs only.
- `runtime_desired_count=1` remains the default.
- No assumption of simultaneous model teams.
- Every stage is resumable through a markdown context packet.
- Admin approval is represented as a status boundary, not bypassed.

#### Task lifecycle

1. Intake.
2. Architecture clarification.
3. Development/content production.
4. Unit or fact testing.
5. Integration testing / consistency review.
6. Optimization attempt: speed, memory, operation count, complexity, UX.
7. Review.
8. Merge/publish plan.

#### Optimization target

The scaffold minimizes runtime dependencies: stdlib Python, SQLite, JSON configs and filesystem artifacts. YAML files are provided as human-readable mirrors.

## Fragment 24: modelstore

### ModelStore

ModelStore is NoemaForge' local, offline-first storage for LLM/SLM artifacts.

#### Goals

- Portable: you can move models in/out of the machine without reinstalling NoemaForge.
- Auditable: changes are logged in SEL (append-only security log).
- Contract-driven: **which models may be used by which roles** is an epoch contract.

#### Directories

- `/var/lib/modelstore/models/<model_id>/model.gguf` (legacy MVP layout)
- `/var/lib/modelstore/models/<model_id>/manifest.yaml` (future)
- `/var/lib/modelstore/model_registry.json` (generated inventory)

Scorecards (surgeon tests):

- `/var/lib/noemaforge/model_scorecards/<model_id>/<stream>__<role>__<cap>.json`

#### Registry scan

The registry is updated by:

- `brainctl models scan --write` (manual)
- `noemaforge-modelscan.timer` (periodic)

#### Role routing

Roles should **not** hardcode model IDs.

If a role omits `args.model`, ToolProxy selects a model using:

1) Epoch contract: `role-model-policy.yaml`
2) Local inventory: `model_registry.json`
3) Optional scorecards: `/var/lib/noemaforge/model_scorecards/...`

Explicit model requests are rejected unless the epoch policy allows it.
